# Rook 0.21.21

The TUI reads sessions, tools, skills, memory, checkpoints, documentation, models and store panels in the background. A slow daemon read leaves draft editing, streamed progress, questions and Stop responsive. Repeated refreshes coalesce to the latest selection, and stale responses cannot replace newer state. Failed panels retain successful prior data and show the error. Each panel GET has a 15-second deadline and a 32 MiB response limit; accepted results share a 64 MiB serialized budget. See [panel refresh](../tui-panel-refresh.md).

Stopping a turn from another window now notifies every observer, so the original CLI can exit before a withheld model reply. Session listing also recognizes equivalent Windows workspace path spellings. An explicit `/session <id|last>` can open a session before the first panel snapshot arrives, and its later refresh keeps the requested session selected.

Closing a local TUI window now shuts down its owned MCP connections before dropping the asynchronous runtime. This prevents a connected stdio MCP child from keeping Windows exit and the local store lock alive. Pending status and authentication tasks are cancelled. HTTP shutdown is bounded to five seconds; a window connected to the daemon leaves the daemon-owned MCP pool running. See [local MCP shutdown](../tui-mcp-shutdown.md).

The loading and stale-response design was informed by Pi's session selector at `482c1381a00d8d00bc81697e4a980c593db6803e`; Rook's implementation is independent.

Hooks stop waiting for stdin delivery after their child process has exited. Output still drains, nonzero exits still refuse gated requests, and live hooks retain their existing watchdogs. Interactive hooks also stop pending input writes when the child exits. This addresses an observed FreeBSD stall where the child and both output streams had finished but stdin delivery remained pending. See [hook admission failures](../hook-admission-failures.md).

These controls cover panel reads. Separate session-continuation reads, local MCP initialization and operations that change data retain their existing routing and deadlines. An obsolete read already in progress finishes or reaches its deadline before the worker skips the remaining obsolete reads. Functional checks establish responsiveness in the tested scenarios, not whole-agent speed or model quality.

No dependency or minimum Rust version change is included.
