# Архитектура

[English](../architecture.md) · [Русский](architecture.md)

## Общая форма

```
                    ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
                    │  rook (CLI)  │   │  rook (TUI)  │   │   web UI     │
                    └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
                           │                  │                  │ HTTP/JSON
                           │                  │           ┌──────┴───────┐
                           │                  │           │    rookd     │
                           └──────────┬───────┘           └──────┬───────┘
                                      │                          │
                                 ┌────┴──────────────────────────┴────┐
                                 │            rook-core               │
                                 │  Rook: config · env · agent loop   │
                                 │  context budget · file captures    │
                                 └──┬────────┬─────────┬──────────┬───┘
                                    │        │         │          │
                            ┌───────┴──┐ ┌───┴────┐ ┌──┴─────┐ ┌──┴─────┐
                            │rook-store│ │  -skills│ │ -tools │ │  -llm  │
                            └──────────┘ └────────┘ └────────┘ └────────┘
```

Три интерфейса, один движок. CLI, TUI и веб-интерфейс — виды на один и тот же
фасад [`Rook`](../../crates/rook-core/src/service.rs), и это то, что не даёт им
превратиться в три продукта, расходящихся во мнении о том, что агент сделал. Всё,
что может показать веб-интерфейс, может напечатать `rook … --json`.

## Почему части разделены

**`rook-store` ничего не знает про агентов.** Он хранит байты по хэшу содержимого,
дописывает журналы сессий и освобождает место. Он не знает, что такое навык или
чекпойнт: когда сборщику мусора нужно понять, что манифест удерживает свои файлы,
вызывающая сторона передаёт
[раскрыватель](../../crates/rook-store/src/maintenance.rs). Эта граница и держит
хранилище достаточно маленьким, чтобы о нём можно было рассуждать и тестировать
его отдельно.

**`rook-skills` ничего не знает про хранилище.** Он читает каталоги и разрешает
версии против [`Environment`](../../crates/rook-skills/src/env.rs). Сохранять
историю навыка — дело `rook-core`, который пользуется хранилищем. Систему навыков,
работающую только с одним бэкендом хранения, было бы заметно труднее переиспользовать.

**В `rook-llm` нет ветвления по вендору.** Один трейт, одна HTTP-реализация
диалекта chat completions, который принимают Ollama, LM Studio, llama.cpp, vLLM и
OpenAI. Провайдеры со своим форматом провода — Messages API у Anthropic,
`generateContent` у Google — получают собственную реализацию того же трейта, и
цикл агента никогда не узнаёт, кто из них отвечает.

Обёртки вокруг этого трейта — снова тот же трейт, и это то, что избавляет цикл от
необходимости знать хоть про одну из них: `Retrying` пережидает всё, что значит
*позже*, `Limited` считает, сколько запросов может быть у одного endpoint'а
одновременно, `Failover` держит список из `[models]` и уходит с endpoint'а,
которого нет, а `Proxy` решает, уходит ли запрос через прокси вообще. Порядок
важен и выражает то, что имелось в виду: повторы носит каждый кандидат по
отдельности, а failover сидит сверху, так что «позже» отвечается там, где это было
сказано, и передаёт дальше только endpoint, у которого «позже» закончилось. Какой
endpoint получит вызывающая сторона, зависит от того, кто она: ход хочет тот, на
который был направлен, потому что перенос на середине выбрасывает его
закэшированный префикс, а поручение хочет тот, где есть место.

**`rook-contain` — это пол.** Платформенные и capability-файловые операции без
внутренних зависимостей; единственное место, где живёт Win32. Внешние зависимости —
cap-std и платформенные привязки, без сборки нативных C-библиотек, поэтому `cargo
check --target x86_64-pc-windows-msvc -p rook-contain` работает с Mac, тогда как
остальная часть воркспейса — нет. Тянуться к нему может кто угодно: запуск
процесса без окна консоли — такой же его ответ, как и изоляция.

**`rookd` — отдельный бинарник от `rook`.** Контейнер, машина без дисплея или
интеграция с редактором должны уметь поднять бэкенд, не линкуя в него терминальный
интерфейс. Его websocket `/api/chat` выполняет ход и отдаёт его потоком, включая
круг одобрения, так что браузер — это способ пользоваться агентом, а не только
читать, что он сделал.

## Цикл агента

[`AgentLoop::run`](../../crates/rook-core/src/agent.rs) намеренно достаточно мал,
чтобы прочитать его за один присест. На каждом шаге:

1. **Сначала проверка бюджета.**
   [`ContextBudget`](../../crates/rook-core/src/context.rs) сжимает контекст *до*
   запроса, когда оценка переходит порог. Агент, узнающий о лимите из отказа, уже
   потерял ход.
2. **Сборка запроса.** Системный промпт с определённым окружением и *каталогом*
   навыков — карточки, не тела. *Заглушки* инструментов, не полные схемы.
3. **Вызов провайдера.**
4. **Диспетчеризация вызовов инструментов**, включая псевдоинструмент
   `load_skill`, подтягивающий тело навыка в контекст по требованию.
5. **Дозапись всего в журнал сессии**, тела хранятся по хэшу содержимого. Сброс на
   диск делается не на каждое событие — где он делается вместо этого и во что это
   обходилось раньше, см. в
   [storage.md](storage.md#что-может-забрать-отключение-питания).

Два поведения здесь структурны, а не опциональны.

**Постепенное раскрытие.** Сотня навыков стоит несколько сотен токенов за ход
вместо десятков тысяч, а на локальных моделях промпт, забитый инструментами,
обрабатывается примерно на порядок медленнее обычного текста. Карточки и заглушки
— поведение по умолчанию; `lazy_skills` и `lazy_tools` в конфиге их выключают, а
не включают.

Это две разные сделки. Карточка навыка откладывает *тело целиком*, и `load_skill`
его достаёт — модель просит по имени. Заглушка инструмента откладывает только
прозу: первое предложение описания, имя и тип каждого аргумента без пояснений
вокруг них. Доставать тут нечего, потому что инструмент, объявленный без своей
формы, нельзя было бы вызвать вовсе.
`the_whole_advertised_tool_list_stays_within_a_budget` держит оба числа — полные
схемы под 2500 токенов на запрос, заглушки под 1100, что и платится на самом деле,
поскольку ленивая загрузка включена по умолчанию, — и утверждает, что заглушки
стоят меньше половины от полных схем, иначе откладывание ничего не покупает. Тест
живёт в `rook-core`, потому что цикл добавляет собственные инструменты поверх
`rook-tools`, и два самых крупных из объявляемых — как раз из них: сначала тест
жил в `rook-tools` и охранял 729 токенов списка, стоившего 1476. `cargo run -p
rook-core --example schema-cost` печатает, как обстоят дела сегодня. Каждый раз,
когда предел поднимали, коммит говорит, какой инструмент это сделал и что было
урезано до того.

Каталог навыков ограничен `agent.max_skill_cards`, и то, что не поместилось,
называется числом, а не отбрасывается молча: `load_skill` отвечает на незнакомое
имя списком подходящих навыков, так что навык, не попавший в список, всё ещё
достижим по описанию. Каталог отсортирован по источнику, ближайший первым, а имя
разрешает ничьи — по двум причинам, которые здесь совпадают. Раньше предел резал
то, что оказалось последним по алфавиту, так что собственный навык проекта
проигрывал навыку, который Rook поставляет, безо всякого выбора со стороны
человека; и список — это начало запроса, так что порядок, меняющийся между ходами,
обесценивает закэшированный префикс всего, что за ним идёт.

**Окружение в системном промпте.** Модели сообщают ОС, архитектуру и userland, в
которых она работает, и какие тулчейны существуют. Это дёшево и снимает самую
частую кроссплатформенную ошибку в расшифровках агентов — обращение к семантике
GNU `sed -i` на BSD-машине.

## Где лежат данные

```
~/.rook/                 (или $ROOK_HOME)
  config.toml            всё настраиваемое, с ограниченными значениями по умолчанию
  secrets.toml           0600 и никогда не в хранилище: ветвление скопировало бы его
  format.json            версия формата хранилища; более новая отвергается, а не портится
  rookd.addr             где слушает запущенный демон; удаляется при остановке
  store/
    index.redb           метаданные, журналы сессий, refs и мелкие объекты прямо в индексе
    objects/aa/bb/<hex>  содержимое, слишком крупное для индекса
    dicts/<kind>.zdict   обученные словари zstd
    tmp/                 подготовка записи; всё оставшееся здесь — след падения
  skills/<name>/SKILL.md пользовательские навыки
  plugins/<name>/        Agent Plugins: навыки и MCP-серверы вместе
  servers/<name>/        языковые серверы, скачанные `rook lsp install`
  running/               по файлу на идущий ход; оставшийся файл — ход, чей процесс умер
  output/                полный вывод убежавшей команды
  cache/sources/         источники навыков между поисками; удаление стоит одной загрузки
  logs/
```

`running/` и `output/` лежат вне хранилища намеренно. Хранилище допускает одного
писателя, а то, что здесь хранится, должно пережить смерть этого писателя; вывод
команды же — запись агента, а не проекта, и в рабочей копии он попадал бы в каждый
чекпойнт и в каждый `git status`.

Один корневой каталог, а не привычное платформе разнесение по конфигу, данным и
кэшу. Состояние агента — это одна вещь, которую люди бэкапят, синхронизируют и
осматривают целиком, и разнесение её по трём путям, зависящим от ОС, превращает
«куда делась память моего агента» в вопрос в поддержку.

Навыки проекта живут в `<workspace>/.rook/skills` и перекрывают пользовательские
навыки с тем же именем: навык, завендоренный в репозиторий, лежит там намеренно.

## Обработка отказов, намеренная

- **Один сломанный навык не опустошает каталог.** Обнаружение собирает ошибки и
  идёт дальше; `rook doctor` перечисляет, что не загрузилось.
- **Снимок, вышедший за свой бюджет, — это ошибка, называющая бюджет**, а не
  медленный путь, укладывающий 45 ГБ.
- **Файл с содержимым пишется раньше записи в индексе.** Падение между ними
  оставляет осиротевший файл, который заберёт `gc`; обратный порядок оставил бы
  запись в индексе, указывающую в никуда.
- **Сборка мусора — mark-and-sweep, а не подсчёт ссылок.** Счётчики расходятся
  после падения или ручной правки, а хранилище, обсчитавшееся в них, молча удаляет
  живые данные.
- **Каждый объект проверяется при чтении.** Хэш пересчитывается после декодирования.
