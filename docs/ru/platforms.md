# Платформы

[English](../platforms.md) · [Русский](platforms.md)

Linux, macOS, Windows и FreeBSD — поддерживаемые цели. `cargo xtask targets`
печатает текущую матрицу.

| цель | платформа | ci |
|---|---|---|
| `x86_64-unknown-linux-gnu` | Linux | тестируется на `ubuntu-latest` |
| `aarch64-apple-darwin` | macOS | тестируется на `macos-latest` |
| `x86_64-pc-windows-msvc` | Windows | тестируется на `windows-latest` |
| `x86_64-unknown-freebsd` | FreeBSD | тестируется в виртуальной машине |
| `aarch64-unknown-linux-gnu` | Linux | компилируется |
| `x86_64-unknown-linux-musl` | Linux (статически) | компилируется |
| `aarch64-unknown-linux-musl` | Linux (статически) | компилируется |
| `x86_64-apple-darwin` | macOS | компилируется |
| `aarch64-pc-windows-msvc` | Windows | по мере сил |
| `aarch64-unknown-freebsd` | FreeBSD | по мере сил |

*Тестируется* значит, что задание CI гоняет там весь набор тестов.
*Компилируется* значит, что задание её собирает и больше ничего: кросс-проверка
никогда не линкуется с libc целевой системы, что и есть причина, по которой
FreeBSD достаётся виртуальная машина. *По мере сил* значит, что ни один
хостинговый раннер такого не предлагает; код под это написан, и на этом
заявление заканчивается.

За каждой строкой стоит строка в [`ci.yml`](../../.github/workflows/ci.yml), и
`cargo test -p xtask` падает, если эта строка пропала, — так что строка таблицы не
переживёт задания, которое её оправдывало, а иначе эта таблица непременно бы
протухла.

## Что на самом деле ограничивает переносимость

Не Rust. Обследование показало, что поддержка FreeBSD у других агентов ломается
через *дистрибуцию*, а не через язык: CLI у Codex написан на Rust, а его
[поломка на FreeBSD](https://github.com/openai/codex/issues/13802) пришла из
npm-обёртки, ограничивавшей список платформ.

Отсюда следуют два ограничения, и оба архитектурные.

**Никакого рантайма.** Rook поставляется двумя статическими бинарниками. Нет ни
Node, ни Bun, ни Python, ни Docker, которых могло бы не оказаться или которые
могли бы упасть на платформе, не тестируемой их сопровождающими.

**Никакого тулчейна сборки, кроме Rust и компилятора C.** Веб-интерфейс — это
написанный руками HTML без бандлера, потому что добавление JavaScript-тулчейна
делает `npm` обязательным условием сборки на каждой платформе, а FreeBSD — ровно
то место, где это идёт не так.

## Две зависимости на C

Измерено, а не предположено. Кросс-компиляция воркспейса под
`x86_64-unknown-freebsd` с macOS: всё, что на чистом Rust, компилируется, и ровно
две зависимости падают:

- **`zstd-sys`** — вендоренные исходники zstd на C.
- **`ring`** — криптопровайдер для TLS, C плюс ассемблер.

Обе падают по одной причине: у хостового `cc` нет sysroot'а FreeBSD. Ни одна из
них не является проблемой FreeBSD — обе прекрасно собираются *нативно* на FreeBSD,
где компилятор рабочий.

Поэтому CI тестирует FreeBSD в настоящей виртуальной машине
([`vmactions/freebsd-vm`](https://github.com/vmactions/freebsd-vm)), а не
кросс-проверкой. Кросс-проверка была бы дешевле и обошла бы ровно те две
зависимости, в которых регрессия «платформа не поддерживается» действительно
могла бы появиться.

**Почему всё-таки zstd**, при такой цене: сжатие со словарями — это то, откуда
берётся коэффициент хранилища, 37,1× против 8,4× у чисто растовых альтернатив, не
умеющих словарей. Потерять это значило бы выпотрошить центральное утверждение всего
дизайна.

**Почему `ring`, а не `aws-lc-rs`**: `rustls` по умолчанию берёт `aws-lc-rs`,
которому нужны cmake и полный тулчейн C и который является самым частым
препятствием для кросс-компиляции во всей экосистеме. `ring` меньше и
кросс-компилируется несравнимо легче. Это задано явно в features зависимостей
`rook-llm`, а не оставлено на усмотрение значений по умолчанию.

## Поведение, зависящее от платформы

Там, где поведение действительно различается, оно обрабатывается в одном месте, а
не размазано по коду.

**Пути.** `$ROOK_HOME`, иначе `~/.rook` на unix и `%LOCALAPPDATA%\rook` на
Windows. Local, а не Roaming: перемещаемый профиль копируется на сервер при
каждом входе, а здесь лежат сессии, кэши и скачанные языковые серверы — гигабайты,
синхронизировать которые никто не просил.

Раньше было `%USERPROFILE%\.rook` — unix-привычка в одежде windows-пути, о чём
и пришла жалоба. Установка, у которой этот каталог уже есть, продолжает им
пользоваться: перевозить гигабайты под человеком ради опрятного пути — плохой
размен, а отправить его в пустой новый каталог читалось бы как «агент всё забыл».
`rook doctor` говорит, какой из двух в ходу.

`ROOK_CONFIG_DIR` переносит только `config.toml` — для конфигурации, которую
держат в репозитории с dotfiles. `secrets.toml` за ним намеренно не идёт: это
единственный файл здесь, состоящий из одних учётных данных, а каталог, на который
указывают такой переменной, по построению синхронизируют или коммитят. См.
[`paths.rs`](../../crates/rook-core/src/paths.rs).

**Оболочка.** `/bin/sh -c` на Unix, `cmd /C` на Windows. `cmd`, а не PowerShell,
потому что он есть всегда; навык, которому нужен PowerShell, вызывает его явно.

**Userland.** Выводится из ОС: `gnu` на Linux, `bsd` на macOS и BSD, `msvc` на
Windows. Он доступен навыкам как предикат в `requires`/`variants` и заявляется в
системном промпте, потому что различия инструментов GNU и BSD — самая частая
кроссплатформенная ошибка в расшифровках агентов. macOS и FreeBSD автоматически
делят один вариант, в чём и смысл.

**Локальная сеть на macOS.** Доступ в неё выдаётся по одному приложению за раз,
а приложению, которому его не выдали, отказывают с `EHOSTUNREACH` — той самой
ошибкой, что даёт отсутствующий маршрут, мгновенно, не отправив ни одного пакета
и ничего не записав в лог. Модельный сервер в той же подсети оказывается
недоступен ровно так, как выглядит сетевая неисправность, и очевидная проверка
только запутывает: `curl` — бинарь самой Apple, под это правило он не попадает и
достаёт тот же адрес из той же оболочки в ту же секунду.

Разрешение принадлежит приложению, которому приписан процесс, — терминалу, а не
бинарю, — и решается при запуске этого приложения, поэтому включение галочки не
действует на уже запущенный терминал. Оно в Системных настройках →
Конфиденциальность и безопасность → Локальная сеть, и требует перезапуска
терминала. Подсказка к этой ошибке говорит об этом, когда адрес находится в нашей
же сети; см. `advice` в [`rook-llm`](../../crates/rook-llm/src/lib.rs).

**Ограничение путей** лексическое: `..` нормализуется без обращения к файловой
системе, поэтому оно ведёт себя одинаково на регистронезависимых файловых системах
и на Windows и работает для путей, которых ещё не существует.

## Сборка на FreeBSD

```sh
pkg install -y rust
cargo build --release
```

## Изоляция команды

`run_command` изолируется платформой там, где платформа умеет, и результат каждой
команды говорит, что именно применилось.

| Платформа | Изоляция | Ограничения |
|---|---|---|
| macOS | Seatbelt (`sandbox-exec`) | известных нет; объявлен Apple устаревшим, присутствует в каждом релизе |
| Linux | Landlock, без привилегий | сеть только с ядра 6.7 и только TCP — никогда UDP, то есть никогда DNS |
| FreeBSD | пока никакой | режим capability у Capsicum ломает оболочку; jail'ам нужен root |
| Windows | низкий уровень целостности, через запускатор, которым является сам `rook` | сеть не ограничивается никогда; рабочая копия и собственный временный каталог rook'а помечаются низким уровнем, и пометка стойкая |

`[sandbox] isolate = "required"` отказывается выполнять команду там, где таблица
говорит «никакой»; `auto`, значение по умолчанию, выполняет её как есть и говорит
об этом.
