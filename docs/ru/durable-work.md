# Цели в сессиях и задачи по расписанию

[English](../durable-work.md) · [Русский](durable-work.md)

## Длительная работа сейчас

В общем `rook tui` введите `/goal <цель>`. Работа продолжается в текущей сессии:
сохраняются история, модель и права. Общие лимиты времени, шагов и токенов
отключены; ограничения контекста и отдельных этапов остаются. Обычный чат
сохраняет прежние лимиты. Сообщения уточняют цель; `✓ taken up` подтверждает
доставку в контекст, а не выполнение. Ctrl-C ставит на паузу, `/continue`
продолжает. Переключение сессии и закрытие окна не останавливают демон.
После перезапуска runnable-цели восстанавливаются; пауза сохраняется.
В локальном режиме `--alone` `/goal` только задаёт метаданные.

## Tasks: запуск по расписанию

Откройте **F4** или Ctrl-P → **tasks**. Задача хранит расписание; каждый запуск
создаёт отдельную обычную сессию с целью. Результаты и подтверждения находятся
в этой сессии.

- **n** — создание. Enter переходит к следующему полю и сохраняет последнее;
  Shift-Tab возвращает назад, Ctrl-U очищает поле, Escape отменяет ввод.
- Поля: инструкция, расписание, часовой пояс, проект, права, секунды, токены,
  число этапов на запуск. TUI предлагает `TZ`, если задан, иначе UTC;
  браузер предлагает свой пояс. Перед сохранением проверьте пояс.
- **r** — запустить сейчас, в том числе выключенную задачу. Расписание не меняется.
- **p / e** — выключить / включить будущие запуски. Текущая сессия продолжается.
- **[ / ]** — выбрать старый / новый запуск; **Enter** — открыть его сессию.
- **x**, затем **y** — отменить последний запуск; выполненные операции сохраняются.
- **d** — удалить расписание после завершения или отмены последнего запуска.

Поддерживаемые расписания:

| Выражение | Когда |
| --- | --- |
| `once 2026-12-01 03:00` | Один раз в указанную будущую дату |
| `every 30m` | Каждые 30 минут; также `h` — часы, `d` — сутки |
| `daily 09:00` | Каждый день |
| `weekdays 09:00` | По будням |
| `weekly fri 09:00` | По пятницам; дни `mon`–`sun` |

Календарное время считается в явно выбранном IANA-поясе, например
`Europe/Moscow`, `America/New_York` или `UTC`. При переходе на летнее время
несуществующее время повторяющегося запуска пропускается; при переводе часов
назад повторённое время выполняется один раз, при первом наступлении.
Неоднозначная или несуществующая разовая дата отклоняется. Интервалы считают
прошедшие секунды, а не календарные дни.

Каждая сессия использует настройки проекта, skills и релевантную память,
без переписки прошлого запуска. По умолчанию на запуск выделено **3600 секунд,
100 000 токенов и 100 этапов**; все лимиты должны быть положительными.
Уже выполняющийся запрос может пересечь лимит — это не жёсткий лимит счёта
провайдера. Права выбираются явно: readonly, assist или autonomous. По умолчанию
форма предлагает assist. Правила запретов и подтверждений проекта сохраняются.
**Needs input** означает, что нужно открыть сессию и ответить на вопрос или
подтверждение. Отсутствие ответа не даёт автоматического разрешения.

Пока предыдущий запуск работает, ожидает, на паузе, заблокирован или исчерпал
лимит, следующий пропускается. Продолжите его сессию или отмените её через
`POST /api/work/{session}/control` с JSON `"cancel"`. Совместимая команда
`rook task cancel SESSION_ID` также сохранена.

После простоя повторяющиеся запуски, опоздавшие более чем на минуту,
пропускаются: демон ждёт следующего времени. Пропущенная разовая задача
выполняется один раз после возвращения демона. Уже принятый запуск сохраняет
ID сессии при перезапуске; очередь всех пропущенных дат не накапливается.
Это не гарантия однократности внешних эффектов: для прерванной операции
по-прежнему может потребоваться проверка и подтверждение восстановления.

Хранятся не более 64 расписаний и 16 последних запусков каждого. Завершённые
записи исполнения освобождаются после сохранения статуса в истории; журнал
сессии подчиняется обычным правилам хранения. Ошибка проекта или конфигурации
выключает расписание и показывает причину.

## API и необязательный CLI

Расписания доступны через `GET/POST /api/tasks`, управление — через
`POST /api/tasks/{id}/control` (`"enable"`, `"disable"`, `"run_now"`, `"cancel_run"`), удаление —
через `DELETE /api/tasks/{id}`. Создание принимает ULID `id` и `spec` из
`rook-proto::schedule::Spec`. Повтор одинакового запроса создания с тем же ID
безопасен; другой spec отклоняется. «Запустить сейчас» — новый явный запуск:
при потере ответа сначала проверьте историю.

```sh
rook task schedule "Проверь упавшие CI" --when "weekdays 09:00" --timezone Europe/Moscow
rook task list
rook task show TASK_ID
rook task run TASK_ID
rook task disable TASK_ID
rook task enable TASK_ID
rook task delete TASK_ID
```

Параметры создания: `--stance`, `--seconds`, `--tokens`, `--max-iterations`,
`--id` для повтора запроса. Старые `task start`, steer и команды управления
исполнением оставлены для совместимости. Панель Tasks показывает расписания;
для немедленной работы в разговоре используйте `/goal`.

Компьютер должен быть включён, а `rookd` — запущен. Автозапуск после входа или
перезагрузки настраивается через системный менеджер служб (например, launchd
или systemd). Rook сам такую службу не устанавливает. Один `ROOK_HOME` должен
обслуживаться одним демоном.

Тесты покрывают часовые пояса, смену времени, пропущенные даты, запрет
перекрытия, восстановление запуска, перезапуск демона во время запроса модели
и форму TUI. Реального многосуточного прогона модели не проводилось.


## Очередь сообщений

В TUI откройте **message queue** через Ctrl-P или командой `/queue`. Панель
показывает сообщения обычной сессии и текущей цели. Операции выполняются фоновым
обработчиком, поэтому ожидание ответа не блокирует ввод и поток вывода агента.

- **e** — открыть сообщение для редактирования; Ctrl-S сохраняет, Enter добавляет
  строку, Escape отменяет правку. При конфликте несохранённый текст остаётся.
- **d** — отозвать ожидающее сообщение.
- **q** — отозвать сообщение и добавить полный текст в черновик промпта. Уже
  набранный черновик сохраняется; отправки не происходит. Если агент успел принять
  сообщение, операция отклоняется и текст не добавляется повторно.
- **r** обновляет список, **a** включает принятые и отозванные сообщения, **n**
  открывает следующую страницу. Стрелки выбирают сообщение, Enter открывает его.
- PageUp/PageDown или колесо мыши прокручивают просмотр полного текста. При
  выборе другого сообщения позиция сбрасывается; у редактора свой курсор.

В браузере раскройте **Message queue** под перепиской. Доступны кнопки изменения,
отзыва и возврата в черновик. Поле промпта многострочное: Enter отправляет текст,
Shift+Enter или Alt+Enter добавляет строку. Если во время отзыва переключить
сессию, возвращаемый текст дождётся открытия исходной сессии.

Через CLI доступны те же операции, в том числе при работающем daemon:

```sh
rook session queue SESSION_ID
rook session queue SESSION_ID list --all
rook session queue SESSION_ID show REFERENCE
rook session queue SESSION_ID edit REFERENCE --revision 2 "уточнённый текст"
rook session queue SESSION_ID withdraw REFERENCE --revision 2
```

Ссылку `REFERENCE` и номер `revision` берите из списка. Ссылка сообщения цели
содержит идентификатор конкретного запуска: устаревшая вкладка не сможет изменить
сообщение новой `/goal`, даже если сессия и ID сообщения совпали. При конфликте
обновите список. Просмотр очереди сам по себе не запускает и не возобновляет работу.

В чате daemon квитанции показывают ссылку, ревизию и состояние сообщения.
Подтверждение приёма содержит идентификатор из той же транзакции, которая
сохранила принятый текст. Отправка, правки и отзыв через общую очередь или старые
маршруты инструкций обновляют открытые представления работающей сессии. Формат
ответа старых маршрутов не изменён. Запоздавшее уведомление «в очереди» не отменяет
уже показанный приём или отзыв. Приём означает включение в контекст, а не успешное
выполнение инструкции. После переподключения или сокращения истории обновите
панель очереди, чтобы прочитать сохранённые квитанции.

Обычные коррекции во время работающего хода TUI и браузер отправляют через HTTP
с собственным ID и сохранённым адресом очереди (`submission_target`). Повтор
использует тот же адрес, ID и исходный текст. Если цель заменена, прежний адрес
отклоняется, а сообщение не переносится в новую цель. Локальный TUI также
использует сохраняемую очередь, когда ID сессии уже известен.

Выполняющийся агент сохраняет поколение цели, к которой присоединился. Перед
принятием сообщения поколение и сессия проверяются повторно под блокировкой
очереди. Замена или удаление цели останавливает старое выполнение на ближайшей
границе между операциями. Пока цель активна, ожидающие сообщения обычной сессии,
отправленные до `/goal`, сохраняются до присоединения к текущей работающей цели. Это не прерывает
уже запущенную операцию и не добавляет поколение старому пути ввода в памяти.

На окно допускается одна неподтверждённая отправка. В TUI `/queue` → **u**
повторяет её, **c** удаляет только локальную попытку. Она сохраняется при
перезапуске daemon, пока открыто окно TUI, но не после перезапуска самого TUI.
Браузер сохраняет одну попытку в `sessionStorage`: **Retry submission** работает
и после перезагрузки вкладки. Запрос к очереди ограничен 30 секундами; при обрыве
или повреждённом ответе попытка остаётся для повтора. **Forget pending send**
удаляет локальную попытку, а не сообщение на сервере — сначала проверьте очередь.

CLI: `rook session queue SESSION_ID submit "новая инструкция"`. Перед отправкой
он печатает ID и адрес в stderr. Для повтора передайте оба параметра:
`submit --id REQUEST_ID --target TARGET "исходная инструкция"`.
Эта отправка сама не запускает ход и не возобновляет приостановленную цель.

Сокетный `prompt` принимает необязательный `id`. Коррекция во время выполнения
хода или цели с тем же ID и исходным текстом возвращает прежнюю квитанцию;
другой текст с тем же ID отклоняется. Старые клиенты могут не передавать `id`.
CLI и TUI создают ID для каждого промпта, но не сохраняют его для ручного повтора
после неопределённого обрыва. В таком случае используйте очередь с сохранёнными
ID и адресом, особенно при замене цели. Начальные промпты, команды `/goal` и
ранний ввод TUI до получения первого ID сессии пока не имеют идемпотентного приёма.

Общий API: `GET /api/sessions/{id}/queue`, полный текст —
`GET /api/sessions/{id}/queue/{reference}`, изменения — POST в общую очередь.
Размер страницы и превью ограничивают настройки `transcript.page_entries`,
`page_bytes` и `body_bytes`.

## Отложенные сообщения

`/followup <текст>` в TUI/REPL, кнопка **Queue follow-up** в браузере или
`rook session queue SESSION_ID submit --follow-up "текст"` ставят новый ход после
полного завершения текущего хода или всей `/goal`. Лимит, ошибка и пауза не считаются
завершением. До резервирования запуска сообщение можно редактировать или отозвать.
Для HTTP используйте `action: "follow_up"` и `follow_up_target` страницы очереди;
для повторной отправки сохраняйте исходные ID, адрес, режим и текст.

Демон запускает готовые сообщения и в пустующей сессии, в том числе после
перезапуска. За секундный такт проверяется до `work.followup_scan_sessions` ID
(по умолчанию 128, допустимо 1..4096), затем обход продолжается с прежнего места.
Число параллельных запусков ограничивает `work.max_parallel_runs`. Сохраняются
workspace, выбранная модель, effort и stance. Изменения через интерфейс сохраняются
сразу и применяются на границе следующего хода; изменения stance через инструмент
сохраняются на границах ходов. После перезапуска действуют текущие правила конфига,
временные разрешения на инструменты не восстанавливаются. Для сессии, работавшей
только в локальном CLI, сначала отправьте явный промпт через демон: без сохранённых
настроек он не начинает фоновую работу.

После аварийного завершения зарезервированный follow-up сохраняет ID выполнения,
принятый промпт и контекст hook. Принятый промпт и hook не повторяются; записанный
результат используется повторно. Неопределённые побочные эффекты требуют проверки
через `/recovery`. Старые записи без контекста hook и завершённые эффекты подготовки
до приёма промпта также требуют явной проверки. При восстановлении выделяются новые
лимиты хода. Явная отмена сохраняет паузу после перезапуска; `/continue` или другой
явный промпт возобновляет сессию. Ошибка восстановления тоже ставит паузу, причина
видна в очереди.

Для обычной работы `/continue` (также `/go on` и `/carry on`) сохраняет связь с
исходной задачей при смене ID выполнения и перезапуске демона. Сообщения,
поставленные до продолжения или во время него, ждут завершения этой работы;
повторное достижение лимита шагов или времени их не запускает. Другой обычный
промпт начинает отдельную задачу. ID выполнения, записи промптов и результаты
остаются отдельными; поле JSON `continuation` хранит один исходный ID.

Если `/goal` превращает выполняемый follow-up в длительную работу, демон
сохраняет подключённый интерфейс, согласования и настройки до первого этапа
новой цели. Этот этап получает её параметры и вложения. Ожидающие сообщения
прежней цели к новой не переходят: проверьте очередь и при необходимости отзовите
и отправьте их снова. Итоговая сводка описывает последний ход, предыдущие ответы
остаются в истории. Записанные результаты доступны отдельно; работа над одинаковым
поведением интерфейсов ещё продолжается.

### Результаты ходов

`rook session turns SESSION_ID` показывает сохранённые итоги, начиная с новых;
`--json` возвращает тот же отчёт, что `GET /api/sessions/SESSION_ID/turns`.
Для следующей страницы передайте полученный `before` через `--before NUMBER`
(HTTP: `?before=NUMBER`). В TUI используйте `/turns` или `t` в просмотре истории:
`n` читает более старые записи, Enter открывает полный итог, `h` возвращает историю.
В REPL работает `/turns [before]`, в браузере — **Turn results** в панели истории.
Просмотр сохраняет черновик и не запускает работу.

Итог хранит ID выполнения, номер промпта, связь с follow-up или продолжением,
причину остановки, токены, шаги, время и начало ответа. Полный результат читается
частями из истории. Общие счётчики учитывают записанные итоги этой сессии, включая
остановки по лимиту; успешные завершения считаются отдельно. Кэшированные токены
входят во входные, складывать их повторно не нужно. Время — сумма промежутков
от начала до сохранения результата, включая простой при восстановлении. Это
показания провайдера в токенах, не денежная стоимость.

Отчёт указывает начало учёта. Старые ходы, попытки без сохранённого итога и расход
до аварии процесса не восстанавливаются задним числом. Результаты унаследованной
ветки доступны в истории, но не считаются новыми выполнениями дочерней сессии.
Поэтому эта статистика не является полным учётом всех попыток запросов модели.
Прерывания по-прежнему проверяются через `/recovery`.

Результат, готовность очереди и счётчики сохраняются одной транзакцией;
восстановление того же итога не увеличивает суммы повторно. Просмотр ограничен
`transcript.page_entries`, `page_bytes` и `search_events`; даже пустая страница
может содержать курсор для продолжения поиска. Полный итог ограничен существующим
лимитом записи восстановления 8 МиБ. Эти записи не входят в контекст модели и
удаляются вместе с сессией.
