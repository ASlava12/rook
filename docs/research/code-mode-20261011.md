# Code Mode runtime feasibility, 2026-10-11

This records the evaluated, unadopted prototype for item 3 of
[the full adoption scope](../reference-functional-adoption.md). Its ordinary
dispatch, approval, checkpoint, journal and cancellation checks passed, but the
native paired LAN comparison did not establish a benefit. The product integration
was removed; research and the external prototype archive remain.

## Runtime choice under test

The inspected Pi reference uses `quickjs-wasi@3.6.2` (MIT): QuickJS-NG in a
WebAssembly instance, with injected tool capabilities. The independent probe in
[`xtask/probes/code-mode`](../../xtask/probes/code-mode/README.md) uses that exact
dependency, installed outside the repository with lifecycle scripts disabled.
It does not evaluate model scripts in Node's host environment. No filesystem or
network extension, module loader, Node global or credential object is injected.

An embedded rquickjs alternative was inspected in the
[official repository](https://github.com/DelSkayn/rquickjs). Its platform table
marks Windows MSVC support experimental and does not establish the project's
FreeBSD target. Adding a new default native C dependency before proving those
targets would introduce unverified portability requirements. The external WASM
probe avoids making that choice prematurely; it is not yet a bundled product
dependency or a tested cross-platform executor.

Runtime API and string-handle behavior were checked against the installed
package's README and declarations and the
[primary source](https://github.com/vercel-labs/quickjs-wasi). Primitive strings
are checked for VM-side length before host copying. Arbitrary rejection objects
are not converted or read through getters. Output is capped independently by
item count and aggregate UTF-8 bytes; large return values remain inside the VM.

## Executed bounds checks

The initial complete bounds run exited 0 with nineteen checks in
`/tmp/rook-codemode-runtime-tests-bounds-final.log`:

- Sequential dependent calls and actual parallel pending calls return only
  explicitly selected output.
- Node globals and host filesystem/module imports are unavailable; using a
  Function constructor stays inside the guest VM.
- Oversized source is refused before evaluation. Oversized argument/output
  strings reach their limits and copy zero bytes into the host.
- Separate UTF-8 aggregate-output and item-count ceilings are reached.
- Call and pending-call ceilings are reached; catching a limit exception cannot
  start more effects. An oversized host result is refused before VM delivery.
- A host refusal is ordinary rejection data. Arbitrary rejection objects cannot
  run guest getters during diagnostic conversion.
- An actual growing allocation fails with out-of-memory; deep recursion fails
  without trapping the host. A fresh VM still executes after that failure.
- A catch-wrapped infinite loop reaches its 50 ms test deadline. Another thread
  cancels a CPU-bound guest through the shared interrupt flag. A pending host
  invocation receives cancellation when the script expires.
- A promise with no pending host work fails rather than waiting forever.

The first run failed thirteen checks because transient handle scopes disposed
handles that the asynchronous bridge still needed. Retaining the API explicitly
and keeping promise resolver handles outside temporary scopes fixed that
ownership error. A subsequent run identified a queue-drain race: a completed
host call may schedule guest reactions after the current drain. The probe now
drains those reactions before declaring a promise unresolvable. Failed logs
remain `/tmp/rook-codemode-runtime-tests.log`,
`/tmp/rook-codemode-runtime-tests-handles-fixed.log` and
`/tmp/rook-codemode-runtime-tests-drain-fixed.log`.

These observations do not certify the whole host's RSS, all possible VM escape
attempts, or execution on Windows/FreeBSD. The VM allocation cap is 16 MiB;
whole-process and bridge accounting still need explicit integration.

## Engine constraints confirmed from current source

`agent/tools.rs::dispatch_recorded` owns policy-sensitive recovery refusal,
journal admission/completion and normal dispatch. The dispatcher adds gates,
hooks, file checkpoints, write tracking, diagnostics and retained images.
Calling `ToolBox.call` directly would omit those semantics.

An execution journal has one pending operation per session. A script's outer
receipt cannot be reused for simultaneous nested calls. Program calls need
owned child execution scopes linked before any effects, with normal receipts
and parent rewind/recovery traversal. Synthetic provider requests would also
misrepresent model attempts and accounting; provider-free tool frames must reuse
the real dispatcher. These are integration requirements, not implemented APIs.

## Native decision: do not adopt

The terminal `report.json` and `program-analysis.json` retain eight pairs and
all sixteen physical native turns, without retries or raised budgets.

| Observation, eight tasks per arm | Direct calls | Candidate |
|---|---:|---:|
| Fully correct completed native turn | 1/8 | 1/8 |
| Correct answer artifact, regardless of completion | 3/8 | 5/8 |
| Median wall time, including failures | 199.125 s | 203.959 s |
| Reported native outcome tokens, incomplete physical coverage | 432,361 | 490,428 |
| Program executions | 0 | 6 |
| Actual injected tool calls from programs | 0 | 0 |

There are no paired completion wins or losses. The candidate produced two more
correct answer artifacts, but they did not turn into additional completed tasks.
All six programs used the VM without injected calls. The observation therefore
does not measure successful tool batching. Median time increased by about 2.4%;
native token subtotals cannot establish complete physical costs or savings.

The original harness recorded a hash of `target/debug/rook` without freezing the
executable. Full CI ran concurrently and the final binary hash differs. Source
was unchanged during those two processes, but that alone does not prove identical
executable identity for every arm. This limits the evidence further; it does not
justify adopting the optimization or retrying the same run for a better result.
The archived executable is named `rook-post-ci` and has its own manifest hash;
it is not represented as the exact measured executable. Future probe runs copy
the supplied binary into their own equipment directory and check its hash before
each arm. The original frozen probe/report is preserved.

The conditional acceptance criterion was not met. The product module, script
dispatcher, settings/help and prototype-only fixtures were removed selectively.
The external `prototype/manifest.json`, original sources and
`prototype/restore-integration.patch` preserve the investigated implementation.
Activity, conversation recall, browser and ACP work was retained. No installed
daemon, operator configuration or optimization default was changed.
