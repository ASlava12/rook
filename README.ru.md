# Rook

[English](README.md) · [Русский](README.ru.md)

Автономный агент, память которого можно прочитать.

Rook — локальный агент общего назначения (код, исследование, автоматизация),
написанный на Rust и поставляемый двумя статическими бинарниками без рантайма.
Всё, что он делает, он кладёт в компактное контентно-адресуемое хранилище и
считает *возможность это прочитать* функцией, а не отладочным довеском: CLI,
терминальный браузер и веб-интерфейс — три вида на один и тот же движок.

> **Статус: молодой проект, и об этом сказано честно.** Хранилище, система
> навыков, инструменты просмотра, цикл агента, стриминг, MCP, LSP и ACP
> реализованы и покрыты тестами — включая целые ходы по настоящему сокету против
> сервера, говорящего на диалекте провайдера. Способная модель провела агента от
> начала до конца: прочитала файл, сняла чекпойнт, внесла правку, запустила
> компилятор и ответила на проверку цели — одна модель и несколько ходов, то есть
> начало, а не послужной список. Ниже не описано ничего, чего нет; чего нет,
> перечислено в [«Что ещё не сделано»](#что-ещё-не-сделано).

## Зачем ещё один

Каждое решение здесь восходит к конкретному публичному провалу агента, которым
пользуются люди: журнал в SQLite, пишущий терабайты в год; чекпойнты, сделанные
как `git add .` поверх рабочей копии на 45 ГБ; схемы инструментов ценой 5000
токенов за ход; переполнение контекста без возможности восстановиться.
Исследование с цитатами —
**[docs/research/agent-landscape.md](docs/research/agent-landscape.md)**.

Отсюда три следствия.

**Память компактна по устройству.** Контентная адресация, словари zstd,
обученные отдельно для каждого рода объектов, и мелкие объекты прямо в индексе.
На синтетической истории из 3000 ходов и 320 результатов инструментов по 64
различным файлам:

```
logical bytes written by the agent :    23.31 MiB
  after dedup (distinct objects)   :     5.29 MiB
  cold store, standalone zstd      :     0.63 MiB   ratio  8.4x
  warm store, trained dictionaries :     0.14 MiB   ratio 37.1x
  on-disk total (index + objects)  :     4.02 MiB
  end-to-end (logical -> on disk)  :     5.8x
```

Воспроизводится одной командой: `cargo xtask compaction`.

**Память можно осмотреть.** `rook store stat` говорит, во что обходится история
и на что ушло место. `rook session show` печатает любую расшифровку по номеру в
последовательности. `rook store cat` печатает любой объект. То, что агент узнал
о вас, — список, который можно прочитать и из которого можно удалять, потому что
факт, который нельзя убрать, — это факт, незаметно управляющий каждым следующим
ходом. TUI и веб-интерфейс показывают те же данные.

**Навыки версионируются и знают про окружение.** Навык объявляет окружение, в
котором он верен, — ОС, userland, архитектуру, версии языков и инструментов — и
может нести тела под конкретные платформы, вместо того чтобы разветвляться на
`deploy-linux` и `deploy-windows`. Любую правку можно снять, сравнить и откатить.

## Установка

Linux и macOS:

```sh
curl -fsSL https://raw.githubusercontent.com/ASlava12/rook/main/install.sh | sh
```

Windows:

```powershell
irm https://raw.githubusercontent.com/ASlava12/rook/main/install.ps1 | iex
```

Скрипт скачивает сборку под эту машину, сверяет её с `SHA256SUMS` релиза и
отказывается продолжать, если они расходятся, после чего кладёт два бинарника и
встроенные навыки под `~/.local` — больше никуда и без повышения прав. Он не
правит конфигурацию оболочки, а говорит, если каталога нет в `PATH`.
`ROOK_PREFIX` кладёт всё в другое место, `ROOK_VERSION` фиксирует релиз, а сам
скрипт — сотня читаемых строк в этом репозитории, если вы предпочитаете сначала
посмотреть, что именно направляете в оболочку.

Из исходников — нужны Rust и компилятор C (две зависимости несут в себе C, см.
[docs/ru/platforms.md](docs/ru/platforms.md)); ни Node, ни Python, ни Docker:

```sh
git clone https://github.com/ASlava12/rook && cd rook
cargo xtask dist               # сборка, упаковка встроенных навыков, размеры
```

Два бинарника, без рантайма и без разделяемых библиотек — 8,1 МиБ и 7,4 МиБ на
момент написания; `dist` их печатает, так что число здесь можно проверить, а не
принять на веру.

Всё, что агент хранит, — сессии, память, навыки, скачанные языковые серверы —
лежит в одном каталоге: это то, что человек копирует на другую машину, кладёт в
резервную копию и открывает, когда хочет узнать, что агент знает. На unix это
`~/.rook`, на Windows — `%LOCALAPPDATA%\rook`, именно Local, а не Roaming:
перемещаемый профиль копируется на сервер при каждом входе, а здесь гигабайты.
Установка, у которой от прежней версии уже есть `%USERPROFILE%\.rook`, продолжает
им пользоваться, а не переезжает; `rook doctor` говорит, какой каталог в ходу.
`ROOK_HOME` переносит всё; `ROOK_CONFIG_DIR` — только `config.toml`, для
конфигурации, которую держат в репозитории с dotfiles. `secrets.toml` за ним не
идёт: он состоит из одних учётных данных.

В релизах — `x86_64` и `aarch64` для Linux (статические, musl: работают на том
дистрибутиве, который у вас есть, а не на том, что был у сборочной машины),
`x86_64` для Windows и обе архитектуры для macOS. FreeBSD — поддерживаемая цель,
которая собирается и тестируется в CI, но опубликованного бинарника пока не
имеет: соберите из клона.

## Как пользоваться

```sh
rook init                                  # создать ~/.rook, конфиг, хранилище
rook doctor                                # окружение, чем изолируется команда, доступна ли модель
rook config check                          # что в файле не является настройкой и какие endpoint'ы отвечают
rook models                                # что отдаёт настроенный endpoint

rook                                       # поговорить
rook run "перескажи, что изменилось в src/"   # один ход, потоком, для скриптов
rook chat --session last                   # продолжить с того места, где бросили
rook session show last                     # `last` работает везде, где ждут сессию
cargo test 2>&1 | rook run "почему падает?"   # stdin приклеивается к запросу
rook --json run "..." | jq .outcome.reply  # один объект: ответ, токены, изменения
                                           # код возврата 2, если ход не доведён до конца
rook tui                                   # разговор, ^p — всё остальное
rook checkpoint create before-refactor     # или `c` во вкладке Checkpoints в TUI
rook docs add redis                        # прочитать документацию один раз и дальше отвечать из неё
rookd                                      # http://127.0.0.1:7717 — веб-интерфейс и API
rook daemon status                         # где он и та ли это сборка
rook daemon restart                        # после обновления; называет ход, который при этом обрывается
```

Браузер — интерфейс, а не витрина: чат продолжает любую сессию, останавливает
ход, отвечает на запросы одобрения и вопросы агента прямо на месте и отрисовывает
то, что говорит модель; сессию, которую пишет терминал, видно вживую во вкладке
сессий, откуда её можно передать в чат. Списки в селектах стойки и усилия — это
собственные списки движка. С разрешения браузера ход, остановившийся ради
вопроса человеку, шлёт уведомление — ровно для того случая, когда автономный
прогон идёт в фоновой вкладке. Это написанные руками HTML и ES-модули, которые
отдаёт `rookd`, без бандлера и без тулчейна: `cargo build` — и всё
([ADR-0012](docs/adr/0012-hand-written-modules-no-bundler.md)).

В разговоре слэш-команды доходят до того же движка, что и подкоманды:

```
/btw <вопрос>   спросить о работе, не вмешиваясь в разговор
/goal [текст]   для чего эта сессия; агенту это сообщается
/model [имя]    на каком endpoint'е из `[models]` пойдёт следующий ход
/stance [имя]   сколько свободы: readonly, assist или autonomous
/context        во что обходится этот разговор и из чего складывается
/skills [имя]   что применимо здесь или тело одного навыка
/undo           откатить последний обмен вместе с файлами
/rewind <seq>   откатиться к точке в расшифровке
/session  /mcp  /jobs  /diff  /new  /help  /quit
```

`/btw` отвечает из того, что агент уже знает — без инструментов, одним запросом —
и его ответ не попадает в контекст, который агент несёт дальше, хотя и остаётся в
расшифровке. Ctrl-C останавливает текущий ход, не выходя; всё, что он успел
сделать, остаётся в журнале.

Набранное во время хода направляет его, а не ждёт его конца: то, что вы
отправите, дойдёт до модели на следующем шаге, так что ход, идущий не туда,
можно поправить, не выбрасывая уже сделанного, — а если у хода есть отданные
подзадачи, услышат все. Строка помечается `✓ taken up`, когда ход действительно
кладёт её в запрос: в уже отправленный запрос ничего не добавить, а сколько
осталось до конца шага, окно не знает, и без этой отметки ожидание не имеет
видимого конца. В TUI и в браузере — это два интерфейса, умеющие принимать ввод,
пока ход идёт.

### Что агент помнит

```sh
rook store stat                # размер, степень сжатия, разбивка по родам объектов
rook store ls --kind file      # объекты, новые сверху
rook store cat 4f2a9b          # любой объект по короткому хэшу
rook store gc --dry-run        # что недостижимо
rook store prune --dry-run     # что отбросила бы политика хранения

rook search "тот фикс CRLF"           # по всем расшифровкам, с ранжированием
rook session ls
rook session show 01JQ… --from 0 --limit 50
rook session show 01JQ… --json | jq '.[] | select(.kind=="tool-call")'
rook session context 01JQ…            # во что обходится разговор и из чего складывается
```

### Что изменилось

Цикл снимает каждый файл, к которому инструмент собирается прикоснуться, так что
в хранилище уже лежит каждый файл в том виде, в каком он был до первого касания.
Это и есть diff целой сессии, посчитанный без репозитория и для файлов, которые
никогда не были под версионным контролем:

```sh
rook session diff 01JQ…            # unified diff всего, что он изменил
rook session diff 01JQ… --stat     # только имена и счётчики
```

Файл, записанный агентом обратно байт в байт, показан как неизменённый, а его
собственные промежуточные состояния не считаются: точка отсчёта — то, что было до
начала, а не то, что он записал последним.

Сессия привязана к проекту, в котором началась, так что продолжение её по id из
другого места продолжит её *там*, а не здесь: её расшифровка называет файлы того
проекта, и её чекпойнты восстанавливаются в него. `-C` перебивает это, потому что
это решение пользователя.

### Отмена хода

Цикл снимает каждый файл, который инструмент собирается изменить, так что откат
возвращает и рабочую копию, и разговор. `delete_file` и `move_file` существуют
именно поэтому: `rm` и `mv` через оболочку не объявляют ни одного пути, так что
ничего не снимается и откат ничего не вернёт — всякое другое изменение, сделанное
командой, оставляет содержимое хоть где-то, а удаление не оставляет ничего.
Откат ветвит, а не обрезает, так что ходы, мимо которых вы откатились, остаются
читаемыми в родительской сессии.

```sh
rook session rewind 01JQ… --to 12               # разговор и файлы
rook session rewind 01JQ… --to 12 --keep-files  # только разговор
rook session fork 01JQ… --at 12                 # ветвление, файлы не трогаются
```

Восстановление — единственный шаг, который что-то перезаписывает, а перезаписать
он может правку, сделанную руками, которую не держит ни один чекпойнт. Поэтому
состояние на диске сначала снимается — на ту самую ветку, которую он только что
создал, — и команда печатает откат, возвращающий всё назад.

### Что-то, что продолжает работать

`run_command` ждёт, ограничивает вывод и убивает по таймауту, что правильно для
сборки и неправильно для сервера. `background: true` запускает команду и сразу
отвечает идентификатором; `job` читает, что она напечатала с прошлого раза, и
останавливает её:

```
run_command  { "command": "npm run dev", "background": true }   → job001
job          { "id": "job001" }                                 → что напечатала
job          { "id": "job001", "wait_secs": 60 }                → …когда закончится
job          { "id": "job001", "stop": true }
```

`wait_secs` — это то, что превращает несколько команд в одно ожидание вместо
многих: три набора тестов, запущенные вместе и потом дождавшиеся, стоят четырёх
вызовов инструмента, тогда как переспрашивание стоит целого хода каждый раз. Он
ограничен тем же таймаутом, который получила бы команда на переднем плане: то же
ожидание, как её ни запусти.

`/jobs` в чате и в TUI показывает тот же список, не тратя на это ход, и `rook
mcp` предлагает ту же пару, поскольку stdio-сессия живёт столько, сколько её
держит клиент. Реестр принадлежит интерфейсу, а не ходу — построенный на каждый
ход, он убивал бы всё, что в нём есть, между одним ходом и следующим, — и
забирает процессы с собой, когда уходит, потому что dev-сервер, переживший
запустившего его агента, некому остановить. `[sandbox] max_background_jobs`
ограничивает, сколько их идёт одновременно, и отказ называет, какие остановить;
каждая держит последние `max_output_bytes`, которые напечатала, потому что
интересная строка сервера — самая свежая.

### Что предлагает крейт

```
crate_api { "crate": "semver", "entity": "VersionReq" }
```

Сигнатура, восстановленная по памяти, — это угаданная сигнатура, и та, что
компилируется, хуже той, что нет. Ответ уже есть на машине: cargo распаковывает
каждую зависимость в свой реестр, а `Cargo.lock` говорит, какую версию выбрал
этот проект, — так что читаются исходники, а не сеть. Не rustdoc JSON, который
был бы лучше и доступен только на nightly.

Сканер — не парсер: он находит объявления и приписывает методы тому `impl`, в
котором они лежат. Он не видит того, что порождает макрос.

### Чтение страницы

Включено по умолчанию, и «выключено» означает, что инструмент вообще не
предлагается, а не что вызов отклоняется: инструмент, которого модель не видит, —
это инструмент, который она не может решить попробовать.

```toml
[web]
enabled = false     # и тогда отсюда ничего не уходит в сеть вообще
```

`web_fetch` сообщает свой риск как адрес, куда он идёт, так что разрешающее
правило может назвать хост: `allow = ["https://docs.rs/"]`. Редирект, остающийся
на том же хосте, отслеживается, а уводящий с него — возвращается как результат:
одобрение называло адрес, и пройти по нему в другое место означало бы потратить
это одобрение там, куда никто не соглашался. HTML приходит прозой, скрипты и
стили выброшены. То, что приходит, — чужой текст на пути в контекст модели, не
факт и не инструкция, и поэтому ответ всегда говорит, откуда он взят.

`web_search` отвечает через DuckDuckGo, если не сказано иначе, потому что это
единственный вариант, который работает без настройки: ни ключа, ни аккаунта, ни
своего сервиса. Чего стоит этот выбор по умолчанию, стоит сказать прямо: запрос
уходит на их хост, а результаты читаются со страницы, а не из API, так что их
вёрстка может сломать чтение. Обе альтернативы требуют, чтобы сначала было верно
что-то ещё:

```toml
[web]
search     = "duckduckgo"               # по умолчанию: настраивать нечего
# search   = "searxng"                  # свой инстанс: запрос остаётся здесь
# search_url = "http://127.0.0.1:8888"
# search   = "brave"                    # хостинговый, с BRAVE_API_KEY в окружении
# search   = ""                         # никакого: `web_search` вообще не предлагается
```

Риск здесь — адрес движка, а не запрос, так что разрешив свой инстанс, вы не
разрешаете заодно чужой. Движок, названный без нужного ему ключа, не
предлагается вовсе: инструмент, падающий на первом вызове, учит модель больше не
спрашивать.

### Секреты, которыми он пользуется и которые не может утечь

Пароль, нужный агенту, во всём, что он видит, назван по имени, и подставляется
значением только внутри инструмента, на выходе:

```sh
rook secrets add ssh_prod                 # вводится, не эхом, никогда не аргументом
rook secrets add npm --source env:NPM_TOKEN    # или скажите, где он уже лежит
rook secrets ls                           # имена, источники, отвечают ли они
```

```
run_command { "command": "sshpass -e ssh deploy@prod 'systemctl restart api'",
              "secrets": ["ssh_prod"] }
```

Значение становится `$ROOK_SECRET_SSH_PROD` в окружении этой команды и больше
ничем: ни вызовом инструмента, ни журналом сессии, ни хранилищем, ни тем, что
резюмирует сжатие контекста, ни тем, что наследует суб-агент, ни следующим
запросом к провайдеру. Всё, что команда напечатает, возвращается с вырезанным
значением — в той единственной точке, где ответ инструмента становится
контекстом. Запрос одобрения называет секрет, который вызов потратит, так что
видно, что именно выдаётся.

`ssh` читает пароль с терминала и больше ниоткуда, поэтому команде, назвавшей
секрет, дополнительно выдаются `SSH_ASKPASS`, `GIT_ASKPASS` и `SUDO_ASKPASS`,
указывающие на помощник, который печатает унаследованную переменную: значения нет
ни в одном аргументе, а помощник исчезает вместе с командой.

Значения лежат в `~/.rook/secrets.toml`, 0600, открытым текстом — ровно то же
свойство, что у незашифрованного SSH-ключа или у `~/.aws/credentials`. Значение,
которое уже живёт в менеджере паролей, там и остаётся: `env:`, `cmd:op read …` и
`keychain:service/account` говорят, откуда его взять. **Ни один вызов не
возвращает значение** — ни CLI, ни API, ни браузер. Команды `show` не существует.

Чего это не делает — так это не мешает модели напечатать секрет нарочно: команда,
которой можно пользоваться секретом, может вывести его в кодировке, которую не
поймает никакая вырезка.
[ADR-0013](docs/adr/0013-secrets-are-named-never-valued.md) говорит это прямо:
здесь закрыт тот путь, которым секреты попадают в расшифровки на самом деле, —
по неосторожности. Одни и те же секреты — это `rook secrets`, `/secrets` в чате
и вкладка в браузере.

### Документация, которую он держит у себя

Модель, спрошенная про Redis, отвечает из того, на чём её обучали, а это было
годовалым в день выпуска и нигде об этом не говорит. `docs` — альтернатива: он
ищет копию, оставленную на этой машине, а если её нет — находит официальную
документацию, читает несколько страниц и подшивает прочитанное, а не страницу.

```
docs { "topic": "redis", "question": "как устроена persistence" }
docs { "topic": "postgres", "version": "16" }
docs { "topic": "redis", "page": 2 }        # одна из них целиком
```

Хранится проза и рядом с каждым фрагментом — адрес, с которого он прочитан, так
что ответ несёт и то и другое: локальную копию, из которой он сделан, и страницу,
по которой его может проверить кто угодно. Копия — одна на тему и версию,
`latest`, если версия не названа, и повторное чтение темы заменяет копию, а не
добавляет вторую. Сбор ограничен, как и всё, что накапливается:

```toml
[web]
docs_pages = 5          # сколько страниц может стоить одна тема
docs_bytes = 200000     # и сколько может весить набор; проверяется по мере поступления
```

Копия устаревает тогда, когда об этом говорит источник, а не когда она просто
полежала: каждая страница хранится с `ETag` и `Last-Modified`, которые дал
сервер, и `--refresh` запрашивает их обратно с этими значениями — не сдвинувшаяся
страница отвечает 304 без тела, и перечитывается только то, что изменилось.
Зафиксированная версия не портится от возраста, а `latest` может оказаться
неверным на следующий день после чтения; ни на то, ни на другое временная метка
не отвечает.

Тема, у которой нет своего набора, отвечается из соседнего, если такой есть:
вопрос про `redis` находит `redis persistence`, собранный час назад, вместо того
чтобы заново идти на тот же сайт, — и ответ говорит, из какого набора он взят.

Те же наборы — это `rook docs ls | show <тема> | add <тема> | rm <тема>`, вкладка
Docs в TUI и вкладка в браузере: читает агент, а прочитанное — ваше, и его видно.

### Проверять, а не верить

Ход может передать утверждение агенту, который его не делал:

```
verify { "claim": "тесты проходят после правки", "settles": "cargo test -p rook-store" }
```

Проверяющий работает в своей сессии, и все инструменты, что-либо меняющие, у него
изъяты — не «попрошены не использовать», а не выданы, — и он обязан закончить
`VERDICT: holds`, `fails` или `unproven`. Проверяющий, остановившийся без
вердикта (маленькая модель описывает команду, которую запустила бы, и на этом
заканчивает), один раз просится, в своей же сессии, запустить её и определиться.
Ответ, который всё равно этого не делает, засчитывается как непроверенный, а не
как пройденный, потому что «выглядит разумно» — это то, что говорят, прочитав и
не запустив ничего.

Это не песочница: `run_command` по-прежнему может писать. Это разница между
правилом, которое модель взвешивает, и инструментом, которого у неё нет.

Тот же инструмент проверяет утверждение о мире, когда включён `[web]`: найти,
где это сказано, процитировать с адресом и отделить то, что страница
констатирует, от того, что её автор доказывает. И правило, без которого ни то ни
другое ничего не стоит: вердикт проверяющего, который ничего не запустил и ничего
не прочитал, засчитывается как `unproven`, как бы уверенно он ни звучал.
Не потянуться ни к чему — это и есть форма выдуманной проверки, и именно её
должно было отсечь обращение ко второму агенту.

Утверждение, которое сначала не подтвердилось, а потом подтвердилось после того,
как ход что-то записал, тоже возвращается как `unproven` — с именем изменившегося
файла. Попросив проверить, что `add` возвращает сумму аргументов, модель
прочитала файл, получила ответ «он вычитает», правила `lib.rs`, пока не стало
складывать, спросила то же самое ещё раз и объявила утверждение проверенным, — а
это ответ на другой вопрос. Цикл помнит, какие утверждения не подтвердились и что
было записано к этому моменту, так что второй вердикт взвешивается против
первого, а не заменяет его. Утверждение, не подтвердившееся потому, что
проверяющий смотрел не туда, и подтвердившееся, когда он посмотрел куда надо, —
обычный пройденный случай: второй ответ обесценивает именно то, что ход между
двумя вопросами что-то записал.

### Когда маленькая модель уходит в сторону

Цикл держит несколько правил, с которыми большая модель не встречается никогда, а
маленькая встречается каждый ход; каждое найдено запуском настоящей модели в CI и
чтением расшифровки. Вызов инструмента, написанный текстом — `{"name":
"read_file", "arguments": {...}}` в качестве ответа, — считается вызовом, все по
порядку, если названный инструмент действительно предлагался. Ход, который сделал
работу и закончил, не сказав ни слова, один раз спрашивают словами, что он нашёл;
ход, у которого кончились шаги, а последним словом был вызов, спрашивают о том же,
но тянуться ему уже не к чему; ход, чей ответ обрезан лимитом вывода, один раз
просят продолжить. Один и тот же вызов, дважды отвеченный одинаково, — это цикл,
а не вопрос, и третий отклоняется с указанием на уже полученный ответ, если только
между ними что-то не изменило рабочую копию, — тогда счёт начинается заново.
Проверяющего, остановившегося без вердикта, один раз просят закончить, а бюджет
шагов суб-агента никогда не меньше трёх, которые нужны задаче. Ничто из этого не
является повтором: каждое спрашивается однократно, и второе молчание возвращается
как молчание.

### Несколько проектов сразу

Хранилище — одно на `~/.rook` и допускает одного писателя; рабочая копия — одна
на проект. Связанные вместе, они означали, что второй проект — это второй
процесс, а второй процесс — как раз тот, который не может открыть хранилище.
Теперь это разное:

```sh
rookd                                              # один демон
ws://127.0.0.1:7717/api/chat?workspace=/path/to/a  # разговор в одном проекте
ws://127.0.0.1:7717/api/chat?workspace=/path/to/b  # и в другом, одновременно
```

Соединения с одним проектом используют общий движок; у разных проектов свои
движки при одной общей истории, одной памяти и одном поиске. Сколько их держать — `[server]
max_projects`, потому что сколько их запросят у демона, решает тот, кто
подключается. Вытесняются только свободные движки. Если все места заняты
соединениями или ходами, новый проект получает отказ до освобождения места.

Демон принимает loopback-адреса в `Host` и сверяет браузерный `Origin` с этим
адресом. Для обратного прокси или удалённого адреса задайте точные доверенные
значения `host:port`: `[server] allowed_hosts = ["rook.example:8443"]`.
Изменение этого списка требует перезапуска демона.

Два соединения, называющие одну и ту же рабочую копию, тоже работают
одновременно. Вызов, который вот-вот запишет, забирает эти пути на всё время
записи, а второму ходу, потянувшемуся за одним из них, отказывают и называют
удерживающую сессию — отказывают, а не ставят в очередь, потому что полезный
ответ на «туда сейчас пишут» — пойти и заняться чем-то другим. `edit_file` не
понадобилось ничего: он заменяет точный текст, а текста, изменённого другим
ходом, там уже нет.

Более медленная гонка — другая: ход читает файл, другой его переписывает, а
первый записывает обратно то, что прочитал. Чтение фиксирует, кто смотрел, и
`write_file` — единственный инструмент, заменяющий файл целиком, — отклоняется,
если последним смотрел кто-то другой, с предложением взять `edit_file`. Работая в
одиночку, вы всегда последний, кто смотрел, так что с этим и не встретитесь.

Захват снимается, когда вызов возвращается, когда он падает по дороге наружу и
когда прерван удерживающий его ход. Ни один из трёх случаев не покрывает вызова,
который не возвращается вовсе, поэтому у захвата есть и срок; а реестр можно
прочитать, потому что блокировку, на которую нельзя посмотреть, нельзя и
разобрать, когда она заклинила:

```sh
curl 'http://127.0.0.1:7717/api/writing'   # путь, сессия, сколько уже держится
```

`rook run` во втором каталоге по-прежнему открывает хранилище напрямую и
по-прежнему встречает блокировку
([ADR-0006](docs/adr/0006-single-writer-store.md)).

### Rook как инструмент для чего-то ещё

```sh
rook mcp serve          # собственные инструменты Rook по stdio, для любого MCP-клиента
rook mcp serve --yes    # …не спрашивая, для всего, что разрешает список запретов
```

Обратное направление к `[[mcp]]`: вместо того чтобы вызывать чужие инструменты,
это отдаёт файловые инструменты, поиск и запуск команд всему, что говорит по
протоколу, — редактору, локальному хосту моделей, другому агенту. Политика
одобрений стоит перед каждым вызовом, и, когда спросить на этой стороне некого,
запись отклоняется, а отказ говорит, что сделало бы её возможной.

Хранилище при этом не открывается, так что он работает рядом с `rookd` — то есть
ровно так, как нужно, если веб-интерфейс поднят, а редактор должен дотянуться до
тех же инструментов.

Все три интерфейса выполняют ходы, отдают их потоком и запрашивают одобрения
одинаково: `rook chat`, `rook tui` и веб-интерфейс на `rookd`. Ничто не доступно
из одного и недоступно из остальных.

### Понимание кода

Машина, на которой языкового сервера нет, может его получить. `rook lsp install
rust-analyzer` берёт последний релиз, сверяет байты по мере получения с
дайджестом, который релиз объявил для этого файла, и кладёт бинарник под каталог
состояния — туда агент смотрит раньше, чем в `PATH`, и удаление каталога отменяет
всё это. Команда печатает, что проверено, а что нет: загрузка цела; сам релиз
никто не рецензировал. `typescript-language-server`, `pyright` и `gopls`
ставятся так же своими средствами — npm под наш префикс с выключенными
install-скриптами, тулчейн Go, собирающий из исходников, — и каждый говорит, что
покрывает проверка его издателя. clangd поставляется zip'ом с деревом, нужным его
бинарнику, и хранится целиком. Агент это тоже замечает: язык, файлы которого
здесь есть, а сервера нет, предлагается один раз за сессию, и дальше решает
стойка — на `assist` выбирает человек, `autonomous` качает в каталог состояния,
`free` пользуется установщиком самой машины. Установленное начинает работать со
следующей сессии.

Когда языковой сервер есть в `PATH`, агент получает ещё четыре инструмента: что
тайпчекер думает о файле, где определено имя, что на него на самом деле
ссылается и где в рабочей копии живёт символ. Он спрашивает по имени — тому,
которое видит в исходнике, — а не по строке и колонке:

```sh
rook lsp servers                              # что применимо здесь
rook lsp diagnostics src/main.rs              # без запуска сборки
rook lsp definition src/main.rs parse
rook lsp references src/main.rs parse
rook lsp symbol ObjectId
rook lsp install rust-analyzer                # скачан, проверен, лежит под ~/.rook
rook lsp update                               # перекачать то, что стоит; сказать, что сдвинулось
```

rust-analyzer, gopls, clangd, typescript-language-server и pyright определяются
автоматически; `[[lsp]]` в конфиге это перебивает. Серверы запускаются лениво, на
первом вопросе, которому они нужны. Поставить сервер — не то же решение, что
воспользоваться уже стоящим, поэтому это следует стойке: рабочая копия с
Rust-файлами и без `rust-analyzer` — это вопрос при `assist`, загрузка при
`autonomous` и открытый вопрос в итоге хода при `readonly`. Сервер, полученный
таким способом, предлагается снова тем же порядком, когда становится старше
`[agent] server_update_after_days` (тридцать по умолчанию, ноль — никогда): иначе
однажды скачанный сервер — это сервер, про обновление которого кто-то должен
помнить. `[agent] install_servers = false` выключает оба предложения.

### Хуки

Команды, выполняющиеся в определённых точках хода, — чтобы расширять агента, не
меняя его:

```toml
[[hooks]]
event   = "post_tool"                    # напечатанное дописывается к результату
match   = "/^(write_file|edit_file)$/"   # обычная подстрока или /регулярка/
command = "cargo fmt --all 2>&1 | tail -3"

[[hooks]]
event   = "pre_tool"                     # может разрешить, спросить или запретить
match   = "run_command"
command = "my-policy-check"              # {"decision":"deny","reason":"…"} в stdout
```

Пять событий: `session_start`, `prompt`, `pre_tool`, `post_tool`, `turn_end`. Хук
читает JSON со stdin и может ответить JSON'ом; обычный вывод считается контекстом
для модели, так что `echo` работает. Хуку `post_tool` дают и то, что инструмент
измерил, а не только то, что он сказал: `is_error`, `truncated`, `full_bytes` и
объект `meta` с теми фактами, которые инструмент записывает, — например, какой
MCP-сервер ответил или упёрлась ли команда в таймаут. Упавший хук `pre_tool`
блокирует вызов, который он охранял, — охрана, которая не смогла отработать, не
является разрешением, — и никакой хук не открывает того, что запрещает список
запретов.

### Модели

`provider/model` в `config.toml` выбирает диалект провода:

```toml
[agent]
model  = "anthropic/claude-opus-5"  # ANTHROPIC_API_KEY
effort = "high"                     # low | medium | high | xhigh | max
prompt_cache_ttl = "5m"             # 5m | 1h — см. ниже
# compaction_model = "ollama/qwen3:8b"   # сжать отрезок — это не суждение
# model = "ollama/qwen3-coder:30b"  # локальный endpoint, ключ не нужен
# model = "openai/gpt-5.5"          # OPENAI_API_KEY
# model = "google/gemini-2.5-pro"   # GEMINI_API_KEY или GOOGLE_API_KEY
```

Три диалекта поддержаны напрямую — Messages API у Anthropic, `generateContent` у
Google и chat completions у OpenAI, — и последний покрывает `lmstudio`, `ollama`,
vLLM, llama.cpp и всё остальное, что ему отвечает. Endpoint, отказывающийся
принимать описания инструментов, получает их в промпте (`[agent] native_tools =
false`), а ответ модели разбирается на вызовы; тот же разбор применяется и с
нативными инструментами, потому что маленькая модель, получив их, всё равно
временами отвечает JSON-объектом: это считается вызовом, если назван
предлагавшийся инструмент, и ответом, если нет. Отказ, называющий их, так и
говорит, потому что эта настройка и есть ответ, а по JSON провайдера его никто не
найдёт.

Локальный движок не обязан стоять на этой машине: `OLLAMA_HOST` и
`LMSTUDIO_HOST` указывают на другую — `LMSTUDIO_HOST=http://192.168.1.46:1234`
это модель на соседнем столе, — а `ROOK_LLM_BASE_URL` делает то же для
`openai-compatible`. Endpoint в своей сети запрашивается напрямую, что бы ни было
в `http_proxy`: прокси в окружении — это прокси в интернет, и запрос к соседнему
столу, пущенный через VPN, возвращается тем, что туннель сделает с адресом,
который не умеет маршрутизировать. Ключ по-прежнему не уйдёт открытым http никуда,
кроме этой машины, — своя сеть тут не исключение.

Запрос, отклонённый из-за того, что добавил агент, а не вы, повторяется без
этого. Принимает ли модель reasoning effort, решается по её имени, и шлюз,
отдающий под этим именем что-то другое, — как раз тот случай, когда имя неверно:
маршрут отвечает 400, и вместо того чтобы завалить ход на поле, которого вы
никогда не задавали, усилие снимается и запрос делается ещё раз — и больше не
шлётся до конца прогона.

`prompt_cache_ttl` — это выбор, по какую сторону паузы вы платите. Запись в кэш
стоит дороже при часовом сроке, а попадание стоит десятую часть в обоих случаях,
так что `1h` окупается ровно тогда, когда разговор переживает пять минут, — то
есть когда человек думает между ходами. По умолчанию его нет, потому что
скриптовый `rook run` никогда не прочитает кэш, который записал его единственный
ход, и просто заплатит за него больше.

Одна переменная на провайдера означает один endpoint на провайдера, а машина, на
которой стоит модель и за которой есть платный API, устроена не так. Endpoint'ы
можно назвать, и тогда `model` — имя из этой таблицы:

```toml
[agent]
model = "desk-large"               # имя ниже или спецификация provider/model

# Куда посылать запрос. Один сервер обычно отдаёт несколько моделей, поэтому
# адрес, ключ и очередь пишутся один раз.
[endpoints.desk]
api = "openai"                     # openai | anthropic | google — диалект
url = "http://192.168.1.100:8080/v1"
key = "secret:desk"                # secret:<имя> | env:<VAR> | само значение
parallel = 2                       # запросов к этому серверу одновременно; 0 — без предела
key_in_the_clear = true            # этот в нашей сети, а не в интернете

# Что у него просить.
[models.desk-large]
endpoint = "desk"
model = "qwen3-30b"
context_window = 120000            # для самостоятельно поднятого — догадка
priority = 1                       # место в очереди перебора; отсутствие — никогда

[models.desk-small]
endpoint = "desk"                  # та же очередь: перемежаются запросы
model = "qwen3-4b"                 # к процессу, а не к модели
priority = 2

# Источник может нести собственный адрес — это случай «один сервер, одна модель».
[models.laptop]
api = "openai"
url = "http://127.0.0.1:1234/v1"
model = "qwen3-coder:30b"
priority = 3
```

`parallel` — причина, по которой две половины разделены, и по умолчанию он равен
единице. Хостинговый API обслуживает то, что ему прислали; llama.cpp и LM Studio
держат одну модель и обслуживают второй запрос, перемежая его с первым, так что
два суб-агента против одного локального сервера закончат позже, чем те же два по
очереди, — и статуса для этого нет, есть только запрос, который идёт минутами и
читается как зависший ход. Счёт ведётся на весь процесс, так что суб-агент, сжатие
контекста и второе окно встают в одну очередь.

Endpoint, до которого не удалось достучаться, выбывает из ротации со строкой в
логе, и берётся следующий по `priority`; `rook models --recheck` возвращает его —
для пополненного баланса или включённого сервера. Дом, работа и выключенная
домашняя машина — это три набора достижимых endpoint'ов и один файл, ради чего
`priority` и существует, и почему источник без него используется, только если
назван явно: платный шлюз не должен становиться тем, за чем агент тянется, когда
машина на столе спит.

Сколько агент ждёт модель — это одно число: `[agent]
stream_idle_timeout_secs`, сколько endpoint'у позволено молчать. К ожиданию
*первого* токена прибавляется то, что должно уйти на чтение промпта: локальная
модель, набивающая большой контекст, молчит минутами по устройству, и больше
ничто это не ограничивает. И не должно: дедлайн на весь запрос — это часы на
ответ, а не на молчание, и десятиминутный, который здесь стоял, резал ответ,
приходивший по токену, и докладывал об этом как `operation timed out` — что
читается как «endpoint пропал», и так и читалось. Ответ, который всё ещё идёт,
не опаздывает.

Пока агент ждёт, он это говорит — во всех интерфейсах: `waiting on the model —
4m20s so far, up to 21m30s`, через двадцать секунд и дальше каждые полминуты.
Эта строка и есть вся разница между моделью, читающей длинный промпт, и упавшим
туннелем, которые иначе выглядят одинаково — пустым экраном.

Ключи могут не лежать в файле. `secret:<имя>` читает `rook secrets`, который
держит значение с правами 0600 или переадресует его в связку ключей, менеджер
паролей или команду; `env:<VAR>` читает окружение этого процесса — там ключи и
лежали до появления этой таблицы. Само значение тоже допустимо и стоит в этом
списке последним намеренно: `config.toml` — не `secrets.toml`, у него не 0600,
это тот файл, который люди вставляют в issue, и тот, который оказывается в
репозитории с дотфайлами. Спецификация `provider/model` по-прежнему берёт ключ из
окружения, и в ней ничего не изменилось.

До каких-то API можно добраться только через прокси, а на той же машине другие не
должны к нему приближаться, поэтому это записывается по частям, а не задаётся один
раз:

```toml
[proxy]
url = "socks5://127.0.0.1:1080"    # http:// | https:// | socks5:// | socks5h://

# Каждая часть берёт строку выше, если не сказала иного. `direct` — то, чем одна
# часть отказывается от прокси, который нужен остальным.
models  = ""                       # API моделей
web     = "direct"                 # web_fetch и web_search
mcp     = ""                       # MCP-серверы по http
install = ""                       # загрузка языкового сервера

[endpoints.paid]
url   = "https://api.example.com/v1"
proxy = "http://gateway:3128"      # этот один endpoint, что бы ни говорил `models`
```

Пустое значение — это не «без прокси», а «здесь ничего не сказано», и тогда
решают `http_proxy` и `no_proxy`, ровно как решали до появления всего этого.
«Без прокси» — это `direct`.

Что бы там ни было написано, запрос к этой машине или в эту сеть уходит напрямую:
прокси — это дорога в интернет, и запрос к соседнему столу, пущенный через него,
возвращается тем, что туннель сделает с адресом, который не умеет
маршрутизировать. У MCP-сервера, который эта машина сама запускает и с которым
говорит по пайпам, сети между ними нет вовсе, и прокси он не видит никогда.

`rook config check` читает файл, называет всё, что в нём не является настройкой,
и спрашивает каждый endpoint, на месте ли он. `rook config set agent.model
desk-small` меняет одну строку и оставляет комментарии вокруг неё как есть.

`rook models` спрашивает endpoint, что он отдаёт. Усилие применяется там, где у
провайдера есть такое понятие; суб-агенты и `/btw` работают на `low` независимо
ни от чего, поскольку ограниченному поручению не нужна глубина, нужная основному
ходу.

### Работа над одной целью дольше одного хода

Ход заканчивается, и кто-то должен решить, будет ли следующий. Если этим
занимается та же модель, что делала работу, длинный прогон — это модель,
проверяющая собственную домашнюю работу, пока не кончится бюджет. Поэтому
проект записывает, по чему его судят, а запускает это обвязка:

```toml
# .rook/evaluation.toml — принадлежит человеку, а не агенту
[[check]]
name = "tests"
run  = "cargo test --workspace"
guards = ["crates/*/tests/**"]   # менять их можно, но это попадёт в отчёт

[[check]]
name = "coverage"
run  = "cargo llvm-cov --json | jq .data[0].totals.lines.percent"
measures = "coverage"            # за этим следят, а не отсекают по нему
```

```sh
rook eval                        # прогнать проверки и сказать, что они сказали
rook work "make the tests pass"  # ходы над одной целью, пока не сойдётся
rook work "keep the docs current" --keep-going --tokens 2000000
rook work --resume               # продолжить последний прогон в этой копии
```

`rook eval` — команда, а не инструмент: модель не может её вызвать, потому что
агент, который может запустить собственную оценку, запустит её до зелёного.
Настоящая независимость кодящему агенту недоступна — он обязан править
репозиторий, а тесты лежат в репозитории, — поэтому scorecard даёт другое:
свидетеля. Сторожимые файлы и сама карточка хешируются до работы и после, и
проверка, позеленевшая в той же итерации, в которой её переписали, говорит об
этом рядом с результатом, а не растворяется в нём.

Между итерациями цикл читает то, что намерила обвязка, и то, что говорит
файловая система, — и никогда отчёт хода о самом себе. Регресс называется первым:
модель, которой дали только текущее состояние, не отличает починку от поломки,
которую сама же и внесла. В следующее приглашение попадает конец вывода упавшей
проверки, а два хода подряд без изменений останавливают прогон. Каждая итерация —
своя сессия: семьдесят ходов в одном разговоре никто не оплатит, а переживать
между ними должны рабочая копия, проверки и `.rook/plan.md` — собственный файл
агента, где он ведёт, что сделано, что дальше и что пробовал безуспешно.
Переписывание плана работой не считается.

Запись прогона кладётся после каждой итерации, так что прогон длиной в дни
переживает перезагрузку машины под собой.

### Изображения и вложенный контекст

Выберите модель с поддержкой изображений:

```sh
rook run --image screenshot.png --context component.ts 'Объясни ошибку интерфейса'
```

В REPL и TUI `/attach-image ПУТЬ` и `/attach-context ПУТЬ` прикрепляют файлы
к следующему ходу; `/attachments` показывает количество, `/attachments clear`
очищает очередь. В браузере есть выбор нескольких файлов. Поддержаны форматы
запросов OpenAI-compatible, Anthropic и Gemini. Если модель отклоняет изображения,
Rook показывает ошибку и не повторяет запрос с удалёнными картинками.

До четырёх вложений за ход: PNG, JPEG, WebP или GIF до 2 МиБ каждое и до 4096
пикселей по каждой стороне; текст UTF-8 — суммарно до 256 КиБ. Аудио и другие
бинарные документы не поддерживаются. Текст файлов, имена и надписи на картинках
остаются недоверенными данными. ACP объявляет `image` и `embeddedContext`,
принимает изображения и встроенные текстовые ресурсы, включая соответствующие
base64 blobs. Ссылки служат указателями; автоматического скачивания нет.
Лимит кадра ACP и WebSocket — 16 МиБ.

Байты сохраняются вместе с сообщением: продолжение сессии и форки не требуют
исходного файла. Просмотр истории не выводит base64; оценка контекста учитывает
изображения. Compaction сохраняет новое вложение до первого ответа модели на него
и ограничивает запрос модели четырьмя изображениями. Старые картинки заменяются текстовой историей с явной
пометкой об отсутствии пикселей в контексте. Если детали снова нужны, картинку
следует прикрепить повторно. Исходные байты остаются в хранилище до удаления
истории по обычным правилам хранения.

API: `options.attachments` — массив объектов `{"type":"image","name":"screen.png",
"mime_type":"image/png","data":"BASE64"}` или `{"type":"text","name":"source.ts",
"text":"содержимое"}`.

### Сценарии запуска

Сценарий — файл `.rook/recipes/<имя>.toml` с `version = 1`, шаблоном `prompt`,
параметрами и необязательными `skill`, `model`, `output`, `output_schema`, `limits`.
Формат навыков остаётся прежним. Полный пример — в [английском README](README.md#run-recipes).

```sh
rook run --recipe audit --param scope=crates --yes
```

В чате и TUI: `/recipe audit {"scope":"crates"}`, отключение — `/recipe off`.
В браузере есть поля имени и параметров; API принимает
`options.recipe = {"path":"audit","parameters":{"scope":"crates"}}`.

Параметры объявляются в `[parameters.<имя>]`. Без `default` параметр обязателен;
неизвестные и пропущенные параметры отклоняются до запуска. `{{имя}}` заменяется
один раз, значения в инструкции заключаются в кавычки. Данные сценария не
расширяют разрешения. Запись в указанный сценарием файл проходит обычную проверку
прав; явный `--output` имеет приоритет. То же правило приоритета действует для
схемы результата. Число исправлений задаёт `--schema-retries`.

`[limits]` содержит положительные `steps`, `tokens`, `seconds` и может только
уменьшать текущие лимиты. `model` выбирает текущую модель или имя из `[models]`,
`skill` — уже установленный применимый навык. Файл и переданные параметры
ограничены 64 КиБ каждый, число параметров — 32. Файл должен находиться внутри
рабочего каталога; удалённые сценарии и исполняемые выражения шаблонов не загружаются.

### Восстановление после сбоя

Перед запуском операции Rook сохраняет намерение, затем — её результат.
При перезапуске незавершённые операции с возможными внешними эффектами получают
статус неизвестного результата. Они не повторяются автоматически; изменения
в затронутой сессии и её подзадачах приостанавливаются до проверки.

```sh
rook session recovery <session>
rook session recovery <session> --acknowledge <operation-id> --note "Проверил файл и вывод команды; ..."
```

В чате и TUI: `/recovery` и `/recovery <operation-id> <описание проверки>`.
В браузере записи доступны в разделе сессий. API: GET/POST
`/api/sessions/{id}/recovery`, для POST нужны поля `operation` и `note`.
Подтверждение фиксирует осмотр и снимает конкретную приостановку; оно не означает
успех операции и не запускает её заново. Устаревшие идентификаторы отвергаются.
Перед подтверждением нужно остановить активный ход.

Журнал учитывает инструменты, фоновые команды, хуки, установку серверов,
запись итогового ответа и проверки `work`. Форк сохраняет сведения о неизвестных
эффектах. Обычная очистка защищает активные и требующие проверки сессии;
явное удаление сессии остаётся доступным после осмотра.

`work --resume` сохраняет исходную цель, проверки, лимиты и сессию незавершённой
итерации, в том числе первой. Новые флаги бюджета не заменяют сохранённый план.
Известные результаты проверок используются повторно; изменение наблюдаемых
файлов явно отмечается. Если проверка была выбрана, но её результат не сохранён,
после осмотра нужен новый запуск `work`, чтобы выполнить её снова. Учитываются
известные расходы токенов до сбоя и в подагентах.

Внешний эффект и журнал не составляют общей транзакции: сбой между ними оставляет
неопределённость, которую нужно проверить. Для старых сессий без нового журнала
доступны только ранее сохранённые события.

### Из редактора

`rook acp` говорит на [Agent Client Protocol](https://agentclientprotocol.com) по
stdio — том же протоколе, который уже используют Zed, JetBrains и Neovim, — так
что плагин под каждый редактор не нужен. Потоковый вывод становится
`session/update`, а политика разрешений — диалогом одобрения в редакторе: то же
решение, доходящее до тех же правил, каким бы интерфейсом его ни спросили.

### Что ему позволено

По умолчанию агент спрашивает перед всем, что меняет машину, и отказывает сразу в
том, что запрещает список запретов: никакое одобрение не перебивает запрет.

Одобрение и вопрос ограничены по-разному, потому что остаться без ответа для них
значит разное. Неотвеченное одобрение считается отказом: работа останавливается и
ничего не изменено, что и есть безопасный конец ожидания. Вопрос же задан потому,
что решение настоящее, и ход, остановившийся на нём, выбрасывает всё, что сделал,
чтобы до этого места дойти, — поэтому по истечении `[agent]
decide_alone_after_secs` (по умолчанию полчаса) ход забирает решение себе:
взвешивает предложенные варианты друг против друга, выбирает тот, который лучше
служит цели, и в ответе говорит, какой выбрал и что взвешивал, — чтобы тот, кого
не было, увидел, что за него решили, и мог это изменить. Второй раз тот же вопрос
не задаётся: один ход как-то потратил на это сто девяносто четыре шага.

```toml
[sandbox]
stance = "assist"                  # readonly | assist | autonomous
allow = ["git status", '/^(ls|cat|rg)\b/']   # обычная строка или /регулярка/
ask   = ["git push"]                          # спрашивает даже в autonomous
deny  = ['/(^|[;&|]\s*)(sudo\s+)*rm\s+(-[a-zA-Z]+\s+)*\/(\s|\*|$)/']
allow_outside_workspace = false    # файловые инструменты не выходят наружу, симлинки тоже
isolate  = "auto"                  # изолировать команды, где платформа умеет: off | auto | required
network  = true                    # изолированной команде можно в сеть
writable = []                      # каталоги, куда можно писать помимо рабочей копии, напр. "~/.cargo"
```

Стойка — это то, сколько у агента свободы, и это одна настройка, а не две: режим
одобрений и уровень автономии — один и тот же вопрос, заданный дважды. `readonly`
не меняет ничего; `assist` подтверждает всё, что не разрешено явно, и передаёт вам
развилку вместо того, чтобы решать её самому; `autonomous` выполняет всё, что не
запрещено, — и перед концом такого хода проверяющий, не делавший работы,
спрашивает, достигнута ли цель и не сделано ли запрещённого: цель сессии, а если
она не задана, то то, о чём попросили ход, — и `fails` даёт ему ещё одну попытку.
Суб-агент наследует стойку запустившего его хода и никогда не получает больше.
`mode` и названия `ask` и `auto` по-прежнему читаются.

Стойку можно менять по ходу работы: `/stance` в чате, F2 в TUI, селект в браузере
и опция конфигурации сессии по ACP — всё это одна и та же политика. `rook --yes`
пропускает запросы на один прогон. Прогон без присмотра и без `--yes` отказывает,
а не импровизирует, и говорит, что сделало бы это возможным.

Запрос одобрения показывает, о чём именно он: запись или правка приходят с тем
diff'ом, который они сделали бы, построенным применением ровно тех правок, что
применил бы вызов, к копии, которую никто не пишет. С отступом под приглашением в
терминале, с цветом в панели TUI, в диалоге браузера и содержимым в запросе
разрешения по ACP: одобрение, называющее только путь, даётся вслепую.

Вопрос, заданный человеку, ограничен `[agent] answer_timeout_secs` (десять
минут). Иначе закрытая вкладка или брошенный терминал держали бы ход — а вместе с
ним и единственную блокировку записи в хранилище — столько, сколько живёт процесс.

Логи идут в stderr и в `$ROOK_HOME/logs/rook.log`, на уровне
`telemetry.log_level`, если `ROOK_LOG` не говорит иного, и ротируются один раз на
`telemetry.max_log_bytes`, так что стоят не больше удвоенного значения. Свой
stderr запущенный демон пишет рядом, в `rook-stderr.log`, и этот файл пуст, пока
кто-нибудь не напишет туда, куда `tracing` уже не успевает: паника обрывает
релизную сборку без единого слова, и причина либо там, либо нигде. Никуда ничего
не выгружается; `telemetry.upload` существует, чтобы этот ответ можно было найти,
а не додумать.

Правило, которое не компилируется, не применяется, и цена этого зависит от того,
в каком оно было списке. Отброшенное `allow` означает лишь, что спросят чаще,
поэтому оно сообщается и отбрасывается. Отброшенное `deny` оставило бы границу,
которую пользователь просил и не получил, — поэтому не разобранное правило запрета
отклоняет всё, что меняет машину, пока его не починят, и говорит об этом. Чтение
при этом работает, так что агент может открыть файл и сказать вам, что с ним не
так. `rook doctor` перечисляет такие правила.

Правило запрета закрепляется дважды: за аргументом, чтобы `rm -rf /tmp/scratch` не
был `rm -rf /`, и за позицией команды, чтобы `grep -r mkfs docs/` не был запуском
`mkfs`. Запрет не перебивается ничем — потому правило, срабатывающее на безобидной
команде, отнимает эту команду насовсем.

Разрешающее правило должно покрывать **каждую** часть, а не одну из них: `ls &&
rm -rf ~` — это не `ls`, а запись, затрагивающая `src/main.rs` и `/etc/passwd`, —
не запись внутри `src`. Автоматические allow-правила не покрывают строки с `$`,
обратными кавычками, перенаправлениями (`<` или `>`) или обратной косой чертой,
даже внутри кавычек. Опции, запускающие другие команды или записывающие вывод,
например `find -exec` и `rg --pre`, тоже исключают автоматическое совпадение.
В `assist` такие команды требуют одобрения; запрос объясняет, почему allow-правило
не применилось. В `autonomous` продолжает действовать стойка с учётом deny и ask.
Против пути обычное правило выравнивается по границе каталога, так что `src/` — не
`notsrc/`; регулярное выражение говорит ровно то, что говорит.

Инструмент с MCP-сервера спрашивается так же, как и всё прочее. Rook не видит,
что он делает, а `readOnlyHint` из протокола — утверждение той самой стороны, о
поведении которой идёт речь, поэтому оно повторяется в запросе и никогда не
принимается на веру: правила сопоставляются с именем инструмента в пространстве
имён, так что `allow = ["gh__"]` доверяет одному серверу, а правило запрета может
отнять один-единственный инструмент.

Файловые инструменты ограничены рабочей копией, и граница проходит там, куда путь
ведёт, а не там, как он написан: симлинк внутри рабочей копии, указывающий за её
пределы, отклоняется, и отказ называет, куда он на самом деле вёл.

Команда изолируется платформой там, где платформа умеет. На macOS она идёт под
Seatbelt, на Linux — под Landlock, на Windows — на низком уровне целостности, и во
всех трёх случаях она сама и всё, что она запустит, может писать только в рабочую
копию и во временный каталог, а читать где угодно; сеть — это переключатель
`[sandbox] network`, включённый по умолчанию, потому что сборка тянет свои
зависимости. `[sandbox] isolate = "auto"` — значение по умолчанию, и оно делает
это там, где может; где не может (пока — FreeBSD), команда выполняется как есть, и
результат инструмента об этом говорит, а `"required"` в таком случае отказывает.
Что именно применилось, записывается на каждой команде, а не предполагается:
песочница, которая тихо ничего не сделала, хуже, чем её отсутствие. Landlock
старше ядра 6.7 не умеет ограничивать сеть вовсе и никогда не ограничивает UDP, а
значит и DNS; уровень целостности в Windows не ограничивает её никогда — результат
говорит и это. На Windows рабочая копия и собственный временный каталог rook'а
получают низкую метку целостности, чтобы команда могла в них писать: это стойкая
пометка на каталоге, и только она. Команда, запущенная в терминале редактора, —
команда редактора, а установщик языковых серверов работает без изоляции намеренно,
после того как человек это разрешил.

### Делегирование

Ход может отдать самодостаточные подзадачи свежим агентам и получить обратно
только их выводы. Каждый суб-агент работает в своей сессии с пустым контекстом,
так что широкий поиск или долгий обзор файлов не попадает в разговор, который его
заказал, — а его полная расшифровка потом читаема. Несколько задач идут
параллельно, с ограничением `agent.max_parallel_subagents`. Список подзадач пишет
модель, и одна запись в нём — это агент со своими ходами, поэтому общее число,
которое ход может запустить, считая запущенных его собственными детьми,
ограничено `agent.max_subagents_per_turn`, а бюджет шагов суб-агента может быть
только короче родительского, но не длиннее — и никогда не меньше трёх, нужных
задаче: вызов, взгляд на то, что вернулось, и ответ.

```sh
rook session ls              # подзадачи видны под ↳, привязанные к родителю
rook session show <child>    # всё, что суб-агент на самом деле сделал
```

Вложенность останавливается на двух уровнях, потому что дальше расход токенов
растёт быстрее, чем делается работа.

Там, где `[models]` называет больше одного endpoint'а, поручение уходит на тот,
который свободен, а не на тот, куда был направлен ход. Ход хочет тот endpoint, на
котором начал, — перенос на середине выбрасывает закэшированный префикс каждого
отправленного запроса, — а поручение это ограниченная работа без разговора,
который стоило бы кэшировать, так что суб-агент, вставший в очередь за
собственным родителем на сервере, берущем один запрос за раз, ждёт тот самый ход,
которому он должен был помочь забежать вперёд. `delegate` принимает и `model` —
для подзадачи, которой нужна большая модель или которой нельзя через платную;
поле предлагается только там, где есть из чего выбирать, а ненастроенное имя
отклоняется с перечислением настоящих.

По умолчанию суб-агент работает в том же каталоге, что и запустивший его ход, и двум сессиям
уже отказано в одновременной записи в один файл — второй говорят, какая сессия его
держит. Чего общий каталог не защищает, так это ветку: ребёнок, сделавший коммит,
уносит незавершённую работу родителя вместе со своей, а сделавший checkout или
reset меняет то, что родитель правит прямо сейчас. Поэтому суб-агенту отказано в
`commit`, `checkout`, `switch`, `push`, `reset`, `rebase`, `merge`, `stash` и им
подобных, и сказано, что делать вместо этого. Чтение не тронуто, поскольку
большинству поручений оно и нужно: `status`, `diff`, `log`, `show`, `blame` и
перечисляющие половины тех команд, у которых их две, — `git branch` и `git stash
list`. Идея взята у [OpenResearch](references/README.md).

Для независимых вариантов реализации модель может вызвать
`delegate({"tasks":["реализовать альтернативу"],"isolation":"worktree"})`.
Каждый ребёнок получает отдельный Git worktree от `HEAD`, локальные инструменты
и свой пул языковых серверов. Это работает и с ожиданием, и с `wait:false`.
Исходный workspace должен быть корнем чистого репозитория, включая отсутствие
неотслеживаемых файлов. Несохранённые буферы редактора, подключения MCP и терминалы
родителя не наследуются. Игнорируемые файлы, результаты сборок и содержимое
инициализированных submodule тоже не копируются: сборка может потребовать подготовки.
Фоновые команды изолированного ребёнка останавливаются при его завершении.
Worktree разделяет изменения файлов; дополнительной защитной песочницей он не является.

В отчёте ребёнка указаны сессия и сохранённый путь в `rook-worktrees/` внутри общего
каталога Git. Родителю доступен инструмент `worktree` с действиями `status`, `diff`,
`read` (поля `path`, `offset` и `limit` в строках) и `remove`. Новые файлы перечислены
в поле `untracked` ответа `diff`. Выбранные изменения переносятся обычными инструментами
редактирования после просмотра; автоматического merge или commit нет. Удаление грязной
копии требует явного `discard:true` и проходит обычную политику записи. Откат родителя
сохраняет изолированные изменения ребёнка. `[agent] max_worktrees = 8` ограничивает число
сохранённых копий на репозиторий; ноль запрещает создание. Проверенные копии удаляются
явно. После аварии процесса восстановление доступно через `git worktree list` и
`git worktree remove <путь>`.


### Итоговый ответ в файл и JSON Schema

`rook run --output report.md "Проверь проект"` сохраняет итоговый ответ силами
программы, без вызова инструмента моделью. Путь находится внутри каталога сессии;
символические ссылки в пути запрещены. Запись атомарная, включена в список
изменений и поддерживает `session rewind`. Ошибка записи завершает запуск с
ошибкой. Прерванный запуск может сохранить доступный ответ, но сохраняет код
незавершённой работы.

`--output-schema schema.json` включает локальную проверку JSON Schema.
`--schema-retries 2` разрешает две попытки исправления формата (диапазон 0–3).
При исправлении инструменты недоступны, расходы учитываются в бюджете времени и
токенов того же запуска. Если формат не исправлен, запуск завершается с ошибкой,
предыдущий файл результата сохраняется. Размер схемы ограничен 64 КиБ; ссылки
на локальные `$defs` поддерживаются, чтение схем из сети и файлов запрещено.
Проверяется структура, а не достоверность отчёта. В потоке могут быть черновики;
в файл попадает только итоговый ответ.

В chat/TUI доступны `/output report.md`, `/schema schema.json` и
`/schema-retries 2`; `/output off` и `/schema off` отключают настройки. Они действуют
на следующие обращения в этом окне. В браузере есть блок «Result format and
file». В API сообщение `prompt` принимает `options` с полями `output`,
`output_schema` (объект JSON Schema) и `schema_retries`. Поле `done.reply`
содержит итоговый ответ отдельно от промежуточного потокового текста.

CLI и TUI подают сигнал терминала при завершении или остановке работы и при
ожидании интерактивного ответа или разрешения. `ROOK_NOTIFY=off` отключает сигнал.
Он отправляется только в stderr, подключённый к терминалу, и не попадает в
перенаправленный вывод или JSON в stdout. Звук или визуальное уведомление
определяются настройками терминала.

### Старые результаты и полный вывод команд

Старые результаты могут убираться из контекста модели, оставаясь в журнале сессии.
По умолчанию сохраняются последние восемь результатов и минимум 8000 токенов недавних
результатов. Старый блок сокращается, когда экономия достигает 8000 токенов.
Ответы человека и загруженные skills сохраняются. Каждое такое сокращение один раз
меняет кэшируемый префикс истории; сохранённая граница обеспечивает одинаковое
представление при следующих запросах и возобновлении сессии. Механизм срабатывает
до compaction и не вызывает модель.

```toml
[agent]
prune_tool_results_min_tokens = 8000  # 0 отключает дальнейшее сокращение
prune_tool_results_keep_tokens = 8000
max_replayed_result_tokens = 1000   # начало/конец при восстановлении истории; 0 — целиком
max_worktrees = 8
```

У результатов есть числовой `result_id`. Через
`read_result({"result_id":42,"offset":0,"limit":16384})` модель получает полный
сохранённый ответ; `"source":"output"` выбирает захваченный stdout/stderr команды.
Ответ содержит байтовые смещения и `next_offset`. Вызов без `result_id` перечисляет
идентификаторы, включая результаты до compaction; в этом режиме смещение — номер
события. Полученные страницы повторно не обрезаются перед отправкой модели.
Необязательное поле `session` выбирает прямого ребёнка: родитель может прочитать
результаты его команд.

Захват полного вывода ограничен `[sandbox] max_spill_bytes` (по умолчанию 64 МиБ),
а обслуживание хранилища оставляет `max_output_files` файлов (по умолчанию 100).
Известные значения использованных секретов удаляются до записи на диск, в том числе
при разрыве значения между чтениями из команды. Достижение лимита явно отмечается
как неполный захват. Фоновые задания тоже сохраняют вывод: сначала вызовите `job`, затем используйте
его `result_id` с `source: "output"`. Работающее или остановленное задание отмечается
как неполный захват. Терминалы редактора сохраняют только доступный от редактора
вывод; уже отброшенные им байты восстановить нельзя.
Само сокращение контекста не удаляет ни результаты в журнале, ни файлы вывода.

### Память

Агент может помнить между сессиями, а вы — читать, поправлять и проверять то, во
что он верит:

```sh
rook memory ls                        # что применимо в этой рабочей копии
rook memory search "как устроены деплои"   # ранжированно, с объяснением совпадений
rook memory add --pin --global "никогда не делать force-push в main"
rook memory since 7                   # что он узнал и забыл за неделю
rook memory history                   # каждое записанное состояние
rook memory diff <objA> <objB>
```

Каждый факт несёт, откуда он взялся — сессию и ход, которые его породили, — так
что неверная память прослеживается до сформировавшего её хода. Каждое изменение
пишет новую версию, и именно это делает возможными `since`, `diff` и откат. Факты
имеют область — глобальную или на рабочую копию, — и в контекст попадает только то,
что подходит к текущему запросу, в пределах бюджета токенов.

### Внешние инструменты

Любой MCP-сервер становится инструментом, который агент может вызвать. Объявите
его в `~/.rook/config.toml`:

```toml
[[mcp]]
name = "filesystem"
command = "npx"
args = ["-y", "@modelcontextprotocol/server-filesystem", "."]

[[mcp]]
name = "hosted"
url = "https://example.com/mcp"
headers = { Authorization = "Bearer …" }
```

С `command` говорят по его пайпам, с `url` — по HTTP, который может отвечать и
JSON'ом, и потоком событий.

```sh
rook mcp ls                              # подключить всё и сказать, что предлагается
rook mcp tools filesystem                # его инструменты и их аргументы
rook mcp call filesystem read_file '{"path":"a.txt"}'   # без модели в цикле
```

Серверы подключаются параллельно, и сбой сообщается, не останавливая ход: один
неверно настроенный сервер не должен стоить вам работающих. Инструменты живут в
пространстве имён `server__tool`.

### Навыки

```sh
rook skills ls                 # что применимо здесь и во что обойдётся загрузка каждого
rook skills why deploy         # какая версия выбрана и почему не другие
rook skills new my-skill -d "…"
rook skills capture my-skill -m "первая версия"
rook skills history my-skill
rook skills diff <objA> <objB>
rook skills rollback my-skill <obj>
```

Навыки появляются тремя путями: написаны руками, написаны агентом (`write_skill`
принимает файлы, нужные процедуре, так что python-помощник и вызывающая его
инструкция приезжают вместе) или установлены из источника через `rook skills
search` и `rook skills install`. Как бы навык ни появился, запрос несёт его
однострочную карточку, а не тело; `load_skill` достаёт тело, когда модель
попросит.

Навык — это каталог с `SKILL.md`, формат
[Agent Skills](https://www.webfuse.com/agent-skills-cheat-sheet), так что навыки,
написанные для других агентов, работают без изменений. Каталог под
`~/.rook/plugins` с `plugin.json` — это Agent Plugin, приносящий свои `skills/` и
свои `mcpServers` вместе; см. [docs/ru/skills.md](docs/ru/skills.md). Плагин,
завендоренный в рабочую копию под `.rook/plugins`, приносит только навыки:
репозиторий — не тот человек, который запускает агента, а запись `mcpServers` — это
команда, которую запустят на старте сессии. Нужные вам кладите в `[[mcp]]` в
собственном конфиге, а пропущенные называются на старте, чтобы вы знали, какие.
Rook добавляет два необязательных блока:

```yaml
---
name: in-place-edit
description: Edit files in place across platforms.
version: 1.2.0
requires:                        # закрывает навык целиком
  language: { rust: ">=1.85" }
  tool: { git: ">=2.30" }
variants:                        # подменяет только тело
  - when: { userland: [bsd] }
    body: variants/bsd.md
  - when: { os: [windows] }
    body: variants/windows.md
---
```

`requires` — причина, по которой `rook skills why` может сказать вам, что навык
неактивен из-за отсутствия Docker 27, вместо того чтобы оставить вас гадать. См.
[docs/ru/skills.md](docs/ru/skills.md).

### Постоянные инструкции

Навык загружается по необходимости. Соглашения проекта можно хранить в
`$ROOK_HOME/AGENTS.md` и `<workspace>/AGENTS.md`. Оба файла передаются как
**справочные данные**, вне системного сообщения. Размер каждого ограничен
`[agent] max_instructions_bytes`; обрезка обозначается явно. `rook doctor`
показывает канонический путь, хеш содержимого и текущий уровень доверия.

Файлы, комментарии, страницы, результаты команд и MCP, каталоги навыков,
контекст хуков, память и сводки не являются новыми инструкциями пользователя.
Оболочка передаёт JSON-записи `rook_source` с происхождением и уровнем доверия.
Названия ролей и вложенные записи внутри текста этого уровня не меняют.
Разрешения инструментов проверяются отдельно. В ответах встроенного `ask`
выбор человека отделён от текста вопроса и сообщений об отсутствии ответа.

Чтобы явно доверить проверенные инструкции проекта или навыка, добавьте запись
в **пользовательскую конфигурацию** (`$ROOK_HOME/config.toml`):

```toml
[agent.trusted_sources]
"/канонический/абсолютный/путь/AGENTS.md" = "<body_blake3 из rook doctor>"
```

По умолчанию список пуст. Проверяются канонический абсолютный путь и BLAKE3
точного текста инструкций, передаваемого модели. Для навыка возьмите `origin`
и `body_blake3` из записи `rook_source` события `skill`, которую показывает
`rook session show`: в хеш входят также подпись навыка и список приложенных
ресурсов, поэтому это **не** хеш сырых байтов `SKILL.md`. Перед добавлением
проверьте содержимое. Изменённый или обрезанный текст теряет доверие; удаление
записи отзывает его и при восстановлении истории. Доверие ограничено рабочей
директорией, в которой представлен источник, не выдаёт разрешений инструментам
и не отменяет запрос пользователя. Старые записи навыков без происхождения
остаются данными.

Такая граница снижает риск инъекции, но не гарантирует невосприимчивость модели.
При защитном анализе инструкции внутри подозрительного материала рассматриваются
как предмет проверки. Отказ или блокирующая проблема получают статус `blocked`
(задача не завершена), а не статус успешного аудита. Классификацию завершения
тоже выполняет модель, поэтому она может ошибаться.

## Устройство

```
crates/
  rook-contain  платформенные и capability-файловые операции; без внутренних зависимостей
  rook-store    контентно-адресуемое хранилище: индекс redb, словари zstd, gc, срок хранения
  rook-skills   разбор SKILL.md, определение окружения, разрешение версий и вариантов
  rook-core     движок: конфигурация, цикл агента, бюджет контекста, снимки файлов
  rook-llm      трейт провайдера, HTTP в диалекте OpenAI и Messages API у Anthropic
  rook-tools    чтение/запись/правка/список/поиск/запуск и защиты, дающие ходу пережить себя
  rook-mcp      клиент Model Context Protocol: транспорты stdio и HTTP
  rook-lsp      клиент Language Server Protocol: диагностика и навигация
  rook-acp      сервер Agent Client Protocol, чтобы агента могли вести редакторы
  rook-proto    типы провода, общие для демона, CLI и веба
  rookd         HTTP-бэкенд, websocket чата, встроенный веб-интерфейс
  rook-cli      `rook`: команды и терминальный браузер
web/dist        веб-интерфейс: написанный руками HTML, без шага сборки
docs/           архитектура, формат хранилища, навыки, платформы, ADR, исследование
references/     исходники других агентов как поверхностные сабмодули, чтобы читать
```

`references/` не выкачивается обычным клоном. `cargo xtask refs status` показывает,
насколько каждый закреплённый указатель отстал от upstream: этот разрыв и есть
очередь чужой работы, которую здесь ещё никто не смотрел. См.
[references/README.md](references/README.md).

## Платформы

Linux, macOS, Windows и FreeBSD. FreeBSD собирается **и тестируется** в настоящей
виртуальной машине в CI, а не проверяется кросс-компиляцией, потому что две
зависимости, несущие в себе C, — ровно то, чего кросс-проверка не задействует.
Заявлено девять целей; `cargo xtask targets` печатает, какие тестируются, какие
только компилируются и какие поддерживаются по мере сил, а тест падает, если
строка заявляет больше, чем на самом деле делает CI. Подробности —
[docs/ru/platforms.md](docs/ru/platforms.md).

## Что ещё не сделано

Прямым текстом, потому что дорожная карта, поданная как список возможностей, — это
способ, которым такие проекты теряют доверие:

- **Способная модель провела его один раз, локально.** Восемь сценариев против
  способной модели в LM Studio проходят: чтение, правка, использование того, что
  напечатала команда, делегирование, отказ решить ложное утверждение по памяти,
  перенос файла вместо перенабора, запись навыка и его загрузка в более поздней
  сессии и запоминание факта в следующую. Первые пять прошли с первой попытки и
  без единой из подсказок, которые цикл держит для моделей поменьше, а три
  добавленных позже — единственное живое свидетельство того, что навыки и память
  переживают записавшую их сессию. CI гоняет те же восемь против модели на три
  миллиарда параметров на каждом push'е, где они большей частью падают по
  собственным причинам модели; чтение этих расшифровок нашло здесь десяток
  дефектов, которых не нашёл бы ни один заскриптованный ответ. Без присмотра
  остаётся долгая работа: восемь коротких сценариев — это не рабочий день, и
  против хостинговой модели здесь ничего не запускалось вовсе.
- **Ходу нужно хранилище целиком, и остался один `acp`, который об этом
  говорит.** `rookd` держит единственную блокировку записи, и каждая подкоманда
  `store`, `session`, `skills`, `memory` и `checkpoint` ходит через его API, а не
  отказывает, — тот же вызов, который демон делает на своём хранилище, так что
  реализация одна, а входа два. Ход так не проходит, потому что он пишет по ходу
  дела; `run` и `chat` вместо этого идут в чат-сокет демона — тот же движок и тот
  же разговор с другой стороны — и говорят, каким демоном пользуются. Остался
  `rook acp`: редактор, ведущий его при поднятом `rookd`, встречает блокировку, и
  ему это сообщают ([ADR-0006](docs/adr/0006-single-writer-store.md)).
- **Рассуждение переносится через вызов инструмента, и только у Anthropic.**
  Раньше не переносилось, а это ход, который Anthropic отклоняет прямо: при
  включённом extended thinking вызов инструмента должен вернуться рядом с
  подписанным блоком рассуждения, который к нему привёл. Блок теперь хранится
  целиком — никогда не разбирается и не пересобирается, потому что подпись
  покрывает байты, — и воспроизводится первым в сообщении ассистента до конца
  этого хода. Более ранние ходы не несут его вовсе, чего API и ждёт. Двум другим
  диалектам это не стоит ничего: они ничего не подписывают и ничего не требуют
  назад. Проверено против сокета, воспроизводящего задокументированную форму того
  API, и против живого API — никогда: ключа здесь ни у кого нет. То есть форма
  верна по построению и не подтверждена на практике, о чём стоит сказать прямо,
  потому что это единственный диалект, где ошибка валит каждый ход.
- **Нет структурированного состояния плана.** Агента просят изложить план прозой
  и велят не вести чеклист — намеренно, на основании чужого бенчмарка
  ([ADR-0010](docs/adr/0010-no-todo-tool.md)). Интерфейсу нечего рисовать как
  прогресс.
- **Всё, что агент читает и запускает, хранится открытым текстом.** Чекпойнт
  держит то, что было на диске, включая `.env`, а результат инструмента — то, что
  напечатала команда. С машины ничего не уходит, но и не шифруется ничего, и `rook
  store cat` распечатает любое из этого обратно. `rook search` находит, куда попал
  секрет: он называет файл и снимок, а `rook session rm` с последующим `rook store
  gc` его убирает. Защищает это режим каталога состояния: он создаётся только для
  владельца — и оставляется как есть, если уже существовал, из-за чего `~/.rook`,
  сделанный старой сборкой или оболочкой, остаётся читаемым для всех учётных
  записей машины. `rook doctor` говорит, какие это каталоги, и печатает `chmod`,
  который их закрывает.
- **Изоляция настоящая, но частичная.** Команда, которую попросила модель, идёт
  под Seatbelt на macOS, Landlock на Linux и на низком уровне целостности на
  Windows: она пишет в рабочую копию и во временный каталог и больше никуда, что
  бы она ни запустила. Читать она может везде, потому что сборке нужен её тулчейн
  — с одним исключением: собственный каталог состояния агента, где лежат
  расшифровки и чекпойнты всех проектов, убран из досягаемости на тех двух
  платформах, которые это умеют; уровень целостности ограничивает запись, поэтому
  на Windows он не убран, и результат говорит, какой это случай. Сеть по умолчанию
  открыта, так что команда, которой отказали в записи, всё ещё может отправить то,
  что успела прочитать. У FreeBSD изоляции нет вовсе, и она об этом говорит.
  Правила-шаблоны поверх командной строки остаются сопоставлением по шаблону:
  `curl … | sh` — это одна обфускация от любого правила, и именно они покрывают
  платформу, у которой нет ничего.
- **Отмена покрывает то, что объявил инструмент, а не то, что сделала команда, — и
  теперь говорит, что именно.** Чекпойнт держит пути, которые инструмент назвал;
  `run_command` не называет ни одного, так что никто не держит, какими были её
  файлы, и `rook session rewind` их не вернёт. Чего он больше не делает — так это
  не молчит: после команды рабочая копия обходится на предмет того, что записано с
  её запуска, и эти пути называются в `session changes`, в `/diff` и в браузере —
  отдельно от тех, для которых есть diff, и посчитанными в общем итоге. Ход,
  запустивший `sed -i`, раньше сообщал, что не изменил ни одного файла. Обход
  читает mtime, так что команда, переписавшая файл теми же байтами, тоже попадёт в
  список, а рабочая копия, слишком большая для обхода, скажет об этом, а не
  сообщит, что ничего нет.

## Разработка

```sh
cargo xtask ci             # fmt + clippy + test, тот же гейт, что в CI; печатает, сколько заняло
cargo xtask dist           # релизные бинарники, навыки рядом с ними и размеры
cargo xtask targets        # матрица поддерживаемых целей
cargo xtask compaction     # измерить заявленные выше цифры по хранилищу
cargo xtask load           # замерить работу, приходящуюся на ход; --scale 2 спрашивает, линейно ли
cargo xtask clean          # сказать, во что обходится target/, и освободить
cargo xtask refs status    # насколько разошлись указатели на чужие репозитории
cargo xtask smoke --model … # восемь настоящих сценариев против настоящей модели
cargo xtask bench --model … # плечи, отличающиеся одной переменной, оценка по рабочей копии
cargo test --workspace
```

Гейт печатает, сколько заняли fmt, clippy и тесты по отдельности, прошёл он или
упал: прогон, умерший после четырёх минут сборки и одной секунды clippy, — это
совсем другое утро, чем прогон, умерший сразу. Прогон, сильно отличающийся от
обычного, — это вопрос, а не день, который надо пересидеть: двадцатиминутные
прогоны здесь оказались холодными, с миллионом с лишним файлов, накопившихся в
`target/debug/deps`, ради чего и существует `cargo xtask clean --all`.

`cargo xtask load` — это ответ на «кажется, стало медленно»: он замеряет на
синтетической сессии те части, за которые ход платит заново на каждом шаге —
дозапись в журнал, его воспроизведение, каталог, промпт, поиск — и печатает
стоимость единицы рядом с каждой. Его первый прогон нашёл, что дозапись одного
события стоит девять миллисекунд, из которых восемь — сброс на диск; в коде этого
не написано, и чтением кода это не находилось.

Полная отладочная сборка с тестами — это около 800 МБ в `target/`. Отладочная
информация — только таблицы строк, а у зависимостей её нет вовсе, потому что
полный DWARF на весь граф зависимостей стоит несколько гигабайт и по нему никто
никогда не шагает.
