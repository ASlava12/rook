## 0. Краткое резюме по состоянию проекта

Это **исключительно хорошо написанного** Rust-проект (агент с локальным хранилищем, CLI, веб-UI, HTTP-дамон, LLM-клиенты, MCP/LSP). За время аудита проверены все критически важные участки:

|---|---|---|
| Движок политики (deny/allow) | `rook-tools/src/policy.rs` | Отлично — deny проверяется **до** allow, denial необратим |

## 1. Критичные проблемы

**Критичных (critical/high) проблем, требующих срочного исправления, НЕ ОБНАЖЕНО.**

Ниже — найденные замечания, отсортированные по убыванию риска. Все они имеют низкий потенциал ущерба или уже смягчены архитектурой.

### [LOW-1] Дубликаты в `members` Cargo.toml (косметика)
- **Где:** `Cargo.toml`, строки 3–16: `"crates/rook-mcp"`, `"crates/rook-acp"`, `"crates/rook-lsp"` записаны дважды (в основном блоке и в конце строки 16).
- **Почему это проблема:** Cargo дедуплицирует члены (`cargo metadata` показывает ровно 13 уникальных workspace members), так что сборка не ломается. Но это путает читателя, может ввести в заблуждение при генерации документации/скриптов и нарушает аккуратность манифеста.
- **Риск:** low (косметический).
- **Исправление:** убрать дубликаты из строки 16, оставив один список.

### [LOW-2] Объекты хранилища на диске не имеют явного режима доступа (defense-in-depth)
- **Где:** `rook-store/src/lib.rs`, строка ~267: `std::fs::write(&tmp, &encoded)` → rename в `object_path`. В crate `rook-store` нет ни одного вызова `set_permissions`/`chmod` (проверено).
- **Почему это проблема:** Внешние объекты и `format.json` получают режим из umask процесса (по умолчанию 0644 — world-readable). Хранилище содержит транскрипты сессий. Это смягчено тем, что `~/.rook` создаётся в режиме 0700 (`paths.rs`, `private_dir()`), поэтому другие пользователи не могут до него добраться. Но если владелец вручную расширит права на `~/.rook` (например `chmod 755 ~/.rook`) или появится symlink-обход — объекты станут доступны другим для чтения.
- **Риск:** low (смягчено 0700; потенциальный риск раскрытия транскриптов при неправильной настройке директории).
- **Исправление:** явно задавать `0600` объектам и `format.json` в `put_tx`/`init`, независимо от umask. Это уберёт зависимость от режима родительской директории.

### [LOW-3] Редакция секретов — намеренно негерметична (документировано)
- **Где:** `rook-core/src/secrets.rs`, функция `redact()` (~строки 300–338).
- **Почему это проблема:** редакция работает как простая замена подстрок для значений длиной ≥6 символов. Это не криптографическая защита; специально вставленный секрет модель может напечатать. Авторы прямо пишут, что это «не претендует на абсолютную защиту» — останавливает политика одобрения и sandbox.
- **Риск:** low (известное ограничение, компенсируется политикой/песочницей).
- **Исправление:** не баг, а осознанный дизайн. Можно улучшить эвристику редкции (например по шаблону `ROOK_SECRET_*` в env), но это необязательно.

### [LOW-4] `named()` выполняет каждый `cmd:`-источник секрета при перечислении
- **Где:** `rook-core/src/secrets.rs`, `Vault::named()`.
- **Почему это проблема:** для определения флага `resolves` вызывается `value_of()`, который запускает внешнюю команду (`/bin/sh -c`) для каждого секрета типа `cmd:`. То есть `rook secrets ls` выполняет все `cmd:`-команды. Это ожидаемое поведение (документировано: «run when the value is needed»), но перечисление имеет побочный эффект выполнения кода.
- **Риск:** low (по дизайну; потенциально неожиданно для пользователя).
- **Исправление:** либо запускать команды только по запросу значения, либо явно предупреждать о выполнении при `ls`.

## 3. Аудит инвариантов (предположения функций)

### 3.1 `policy::decide` (`rook-tools/src/policy.rs`)
- **Предположение:** deny-правила и `ruinous` проверяются до allow/grant; stance `ReadOnly` не отменяет их.
- **Где нарушается:** если в deny-шаблоне используется unanchored regex/substring — правило сработает шире (консервативно, не уязвимость). Порядок проверок зафиксирован и покрыт тестами.
- **Эффект:** корректность границы безопасности сохранена.

### 3.2 `in_the_clear` (`rook-llm/src/lib.rs:481`)
- **Предположение:** если base начинается с `http://` и ключ задан, а хост не loopback — ключ уйдёт в открытом виде; поэтому отказываем на старте.
- **Где нарушается:** `host_of` парсит только host через reqwest::Url; IPv6 в `[...]` обрезается. Частные/локальные адреса для plain-http с ключом всё равно отклоняются (строже, чем нужно).
- **Эффект:** безопасность ключей обеспечена; читаемость/сопровождаемость хороши.

### 3.3 `put_tx` / инициализация хранилища (`rook-store/src/lib.rs`)
- **Предположение:** `~/.rook` уже в режиме 0700 (из `private_dir()`).
- **Где нарушается:** если директория создана с более широкими правами — объекты 0644 доступны другим.
- **Эффект для безопасности данных:** потенциальное раскрытие транскриптов; для читаемости/сопровождаемости — ок.

### 3.4 `exec` (process group, orphan detection)
- **Предположение:** `kill(-pgid, 0)` корректно определяет «жив ли» сиротский процесс; таймаут убивает всю группу.
- **Где нарушается:** на платформах без поддержки process-group (Windows low-integrity launcher) — иной механизм, но задокументирован.
- **Эффект для работы библиотеки:** надёжно; для безопасности — сироты не остаются после таймаута.

## 4. Модели атак

### A1. Утечка API-ключа по открытому соединению (plain HTTP)
- **Что может атакующий:** перехватить bearer-ключ провайдера в сети.
- **Пригодные участки:** `rook-llm` — любой провайдер с `*_BASE_URL=http://…`.
- **Как закрыто:** `in_the_clear` отказывает на старте, если base `http://`, ключ задан и хост не loopback/private.
- **Риск в текущем коде:** low (защита есть).

### A2. XSS через веб-UI
- **Что может атакующий:** внедрить JS в транскрипт/результат инструмента, выполнить в браузере владельца.
- **Пригодные участки:** `web/dist/*.js`, `rookd/src/web.rs`.
- **Как закрыто:** `md()` и `el()` строят DOM через `createElement`/`createTextNode`; `innerHTML` не используется для пользовательских данных (проверено).
- **Риск:** low.

### A3. Переход прав через политику (policy bypass)
- **Что может атакующий:** заставить агент выполнить опасную команду в `ReadOnly`.
- **Пригодные участки:** `rook-tools/src/policy.rs::decide`.
- **Как закрыто:** deny + `ruinous` проверяются до grants; stance `ReadOnly` denies всё, что меняет машину (кроме ask). Denial необратим.
- **Риск:** low.

### A4. Побег из песочницы / exfiltrация через чтение
- **Что может атакующий:** команда прочитает `~/.rook` (транскрипты, секреты) и отправит по сети.
- **Пригодные участки:** `rook-tools/src/isolate.rs`, `exec.rs`.
- **Как закрыто:** `Isolation.unreadable` исключает `~/.rook` из доступа (в т.ч. чтение); Seatbelt/Landlock применяются; сеть — переключатель.
- **Риск:** low.

### A5. Побочный эффект перечисления секретов
- **Что может атакующий:** если `cmd:`-источник выполняет вредоносную команду, то `rook secrets ls` запустит её.
- **Как закрыто/смягчено:** только через политику одобрения; по дизайну.
- **Риск:** low.

### A6. (потенциальный) мирочитаемость объектов хранилища
- **Что может атакующий:** при `chmod 755 ~/.rook` прочитать объекты 0644 другим пользователем.
- **Как закрыто частично:** `~/.rook` по умолчанию 0700.
- **Риск:** low (требует ручной настройки).

## 5. Рекомендации по рефакторингу архитектуры

Проект архитектурно зрелый (ADR, чистые слои, `no_panics`, line-tables-only backtraces). Конкретных архитектурных переработок **не требуется**. Возможные улучшения низкого приоритета:

1. **Явный режим объектов хранилища** — вынести установку `0600` в отдельную утилиту и применять к объектам/`format.json`. Уберёт скрытую зависимость от umask/режима родительской директории (усиление defense-in-depth для конфиденциальных транскриптов).
2. **Идемпотентность `named()`** — рассмотреть разделение «перечисления» и «выполнения» `cmd:`-источников, чтобы `secrets ls` не имел side-effect выполнения кода (мелкое UX/security улучшение).

1. **[LOW-1]** Убрать дубликаты в `Cargo.toml:16`. Проверить `cargo metadata --no-deps` — 13 members, без изменения поведения.

## 7. Что НЕ НАЙДЕНО (честно)

Согласно требованию не выдумывать проблемы, подтверждаю отсутствие в production-коде:

- **Нереализованных заготовок / placeholder / `unimplemented!`** — нет (покрытие тестом `no_panics`).
- **Zombie-кода** (есть, но ничего не делает) — нет (`cargo check`: 0 unused).
- **Кода для безопасного удаления без изменения поведения** — только LOW-1/LOW-2.
- **Потенциальных багов логики / runtime panic / crash-сценариев** — не обнаружено (UTF-8 slicing защищён через `str`, `panic = "abort"` + line-tables-only, нет индексации по вычисленным байтам в критических местах).
- **Уязвимостей (XSS, injection, CSRF, SSRF, утечка ключей)** — не обнаружено (защиты на месте).
- **Рейсов / дедлоков** — не обнаружено; синхронизация через `RwLock`/`Mutex` с корректным `.lock().unwrap_or_else(|e| e.into_inner())`, нет вложенных блокировок «везде».
- **Проблем с памятью / утечек** — не выявлено (RAII, no explicit alloc).
- **Дублирующего функционала** — не выявлено.
- **Запутанного/плохо поддерживаемого кода** — код хорошо задокументирован; замечаний нет.
